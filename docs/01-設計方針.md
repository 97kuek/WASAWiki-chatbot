## 0. 前提となる実測値

`dump_wiki.py` による全ページ取得の結果。設計判断はすべてこの数字に紐づく。

| 項目 | 実測 | 設計への含意 |
|---|---|---|
| 本文ページ数 | 117（標準名前空間） | **極小**。分散DBもスケール設計も不要 |
| 総文字数 | 300,425字 | 全文で20〜30万トークン。100万コンテキストに収まる |
| 見出し数 | 865（H2:231 / H3:326 / H4:223 / H5:65 / H6:20） | 階層構造が非常に明確。チャンク境界に使える |
| 節あたり文字数 | 中央値**191字** / 最大6,411字 / 2000字超は17個 | **節そのままではチャンクが細かすぎる**。親へマージ必須 |
| 表（wikitable） | 39個 | 少ない。個別変換で対応可能 |
| テンプレート | **実質0**（DISPLAYTITLE/DEFAULTSORT のみ4件） | ⚠️ **重要**：`action=parse`でのHTML化が不要。wikitext直で読める |
| ファイル埋め込み | 57箇所 / 画像67枚（PNG41・JPEG26） | キャプションが情報を持つ。画像本体の扱いは要検討 |
| 内部リンク | 267 | ページ間の関係グラフが既に存在する |
| 数式・脚注・生HTML | ほぼゼロ | パース例外処理がほぼ不要 |
| 更新の生存性 | 117中68ページが2025〜2026年更新 | 生きたWiki。**更新追随の設計が必須** |

### ここから導かれる基本認識

1. **データが想定以上にきれい**。前回「テンプレート展開のためHTML経由を推奨」としたが、テンプレートが実質ゼロだったため**撤回する**。wikitextを直接扱う。
2. **規模が小さい**。ベクトルDBのインフラを組むより、全件をメモリに載せて総当たりする方が速く正確で安い領域。
3. **構造化のヒントがタイトルとメタデータに既にある**（`空力設計(41st)`、`構造設計 38th`）。ここを機械的に抜けるのが最大のレバレッジ。

## 1. RAG方式の選定：ドキュメント / SQL / グラフ

### 1-1. 各方式の適性評価

| 方式 | 本件での強み | 本件での弱み | 判定 |
|---|---|---|---|
| **ドキュメントRAG**（チャンク＋類似検索） | 本文の大半が非構造の散文・箇条書き。素直に効く | 「歴代の変遷」等の**全域質問に原理的に弱い**。節が細かく文脈が切れやすい | **主軸として採用** |
| **SQL RAG**（Text-to-SQL） | 「41代の翼幅は？」「歴代機体を重量順に」等の**属性クエリ・集計・並べ替えに圧倒的に強い**。決定的で検証しやすい | 対象となる構造化DBが**現時点で存在しない**。表39個は諸元表として不揃い | **限定採用**（後述のメタデータ層のみ） |
| **グラフRAG**（エンティティ＋関係＋コミュニティ要約） | 「代 × 班 × 部品 × 人」の関係が明確で相性は良い。全域質問に強い | 構築コストが規模に見合わない。LLMでのエンティティ抽出・グラフ構築・コミュニティ検出は117ページには過剰 | **不採用**（ただし**利点だけ別手段で回収**、§3参照） |

### 1-2. 結論：ドキュメントRAG主軸 + 軽量メタデータ層のハイブリッド

グラフRAGを見送る根拠を明確にしておく。GraphRAGの本質的な価値は**「コミュニティ要約による全域質問への対応」**であり、グラフ構造そのものではない。そして本件では、その価値は**階層的な事前要約**（§3）で、はるかに安く得られる。117ページという規模では、グラフを組むコストが便益を上回る。

一方でSQL RAGの利点は捨てない。ただしText-to-SQLをやるのではなく、**ページ属性をテーブル化する**という限定的な形で取り込む：

```
pages(page_id, title, 代, 班, カテゴリ, 最終更新日, 更新者, 文字数, 要約, is_stub)
sections(section_id, page_id, パンくず, 見出し, 本文, 文字数)
images(file, キャプション, 掲載ページ, url)
links(from_page, to_page)          -- 内部リンク267本から自動構築
```

これで「41代の資料を見せて」「電装班の全ページ」「今年更新されたページ」といった**属性で絞れる質問は、検索を経由せず確実に答えられる**。ベクトル検索の曖昧さに頼るべきでない領域を、構造化で刈り取る設計。

### 1-3. 提案アーキテクチャ（4層）

```
┌ L0 メタデータ層（SQLite）─────────────────────┐
│  代・班・カテゴリ・更新日で決定的にフィルタ         │  ← SQL RAG の利点
├ L1 目次層（常時コンテキスト、1〜2万トークン）──────┤
│  全117ページのタイトル＋1〜2行要約＋更新日        │  ← 「どこを見ればいいか」を常に把握
├ L2 検索層（ハイブリッド検索）────────────────┤
│  BM25 + ベクトル、メタデータで事前フィルタ         │  ← ドキュメント RAG 本体
├ L3 本文層（ツール経由で取得）────────────────┤
│  get_page / get_section で全文を渡す            │
└ L4 要約層（事前計算、階層的）────────────────┘
   ページ要約 → 班・代別要約 → 全体要約           ← 全域質問対応（GraphRAG の代替）
```

**L1（目次を常時コンテキストに置く）が本設計の肝**。117ページという規模だからこそ、目次全体が1〜2万トークンに収まる。Claudeは常に「Wiki全体に何があるか」を把握した状態で、必要なページだけを取りに行ける。検索の失敗が致命傷にならない。

## 2. 全域的タスクへの対応

### 2-1. 問題

Top-k検索型のRAGは、**「全体を見ないと答えられない質問」に原理的に答えられない**。本件で想定される例：

- 「歴代で駆動系のトラブルはどう変遷した？」（全代を横断）
- 「このWikiで一番情報が薄い分野は？」（全体のメタ認知）
- 「うちのサークルの設計思想を要約して」（全体の統合）

k=5で引いた5チャンクからは、どう頑張っても出てこない。

### 2-2. 手法比較

| 手法 | 仕組み | 本件での評価 |
|---|---|---|
| **MapReduce** | 全ページを個別要約(Map)→統合(Reduce) | 正確。117回のAPI呼び出しは1回$1程度で**許容範囲**。ただしリアルタイムでは遅い（数分） |
| **Refine** | 1件ずつ読んで回答を逐次更新 | **不採用**。117件は長すぎ、順序依存で初期の情報が薄れる。10件程度までの手法 |
| **階層的事前要約** | MapReduceの結果を**事前計算してキャッシュ** | **採用**。全域質問が即答になる。更新分だけ再計算すればよい |

### 2-3. 採用案：階層的要約の事前構築

```
L4-a  ページ要約     117個   （各200字）      = 約2.3万字
L4-b  班別・代別要約   ~15個  （各600字）      = 約0.9万字
L4-c  全体要約         1個   （1500字）
```

全部合わせて**約3.5万字（〜3万トークン）**。これを丸ごとコンテキストに入れても安い。全域質問はここを読むだけで答えられ、リアルタイムMapReduceが不要になる。

**これが実質的な「軽量GraphRAG」**である。GraphRAGのcommunity summaryと機能的に等価な成果物を、グラフ構築なしで得ている。

**更新追随**：MediaWikiの `list=recentchanges` API で変更ページを検出し、**そのページの要約だけ再計算 → 属する班・代の要約を再計算 → 全体要約を再計算**。差分更新なので日次バッチで数円。

### 2-4. 質問ルーター

質問を分類して経路を変える。これが全体の効率と精度を決める。

| 質問種別 | 例 | 経路 |
|---|---|---|
| 属性型 | 「41代の資料一覧」 | L0のSQLだけ |
| 局所型 | 「桟橋の持ち物は？」 | L1目次→L3本文 |
| 横断型 | 「40代と41代の翼設計の違いは？」 | L0でフィルタ→L2検索→L3本文×複数 |
| 全域型 | 「駆動系の課題の変遷」 | L4要約層 |
| 回答不能型 | 「来年の予算は？」 | 「Wikiに記載なし」と答える |

## 3. RIG（Retrieval Interleaved Generation）の採否

### 判定：**不採用**

RIGはGoogleのDataGemmaで提案された、生成の途中で統計値をretrieval結果に差し替える手法。採らない理由：

1. **前提が違う**。RIGの本領は「Data Commonsのような権威ある統計DBと照合して数値を検証する」こと。本件には照合先となる正解DBが存在しない。数値（翼幅・重量・出力）はWiki本文に散在しており、それ自体が検索対象であって検証基盤ではない。
2. **ツール呼び出しループが実質的に上位互換**。Claudeが生成中に「このページを読む必要がある」と判断してツールを呼ぶ挙動は、interleaved retrievalそのものであり、より汎用的。RIG専用の実装を足す意味が薄い。
3. **実装コストが便益に見合わない**。

### ただし思想は取り込む

RIGの核心は**「生成された数値の検証可能性」**にある。これは以下で担保する：

- 数値・固有名詞を答える際は、**出典ページ名と該当節を必ず併記**させる
- 出典が示せない主張は出力しない（評価指標のFaithfulnessで機械的に検出、§4）

## 4. 精度評価アプローチ

### 4-1. 評価は「検索」と「生成」の2層に分離する

これを混ぜると、精度が悪いときに**検索が悪いのか生成が悪いのか切り分けられない**。改善のフィードバックループが回らなくなるため、必ず分ける。

### 4-2. 手法の採否

| アプローチ | 採否 | 理由 |
|---|---|---|
| **BLEU / ROUGE**（n-gram一致） | ❌ **不採用** | (1) 日本語は分かち書きが必要でn-gram一致が不安定。(2) RAG回答は「同じ意味・違う表現」が常態で、表層一致は実力を測れない。(3) 参照回答を人手で書くコストが高い割にLLM判定との相関が低い。**測っても改善に繋がらない指標は入れない** |
| **埋め込みベース**（BERTScore等） | △ **補助のみ** | BLEUよりマシだが「意味は近いが事実が誤り」を検出できない。**回帰検知（前回との差分監視）にだけ使う** |
| **ルールベース** | ✅ **採用** | 安く決定的。出典の有無、代の混同、禁止表現、「わからない」と言うべき質問への挙動。**ガードレールとして必須** |
| **LLM-as-a-Judge** | ✅ **主軸として採用** | RAG評価の現実解。1問数円。下記の指標を使う |
| **人手評価** | ✅ **採用（少量・定期）** | 唯一の真の正解。**LLM判定器のキャリブレーションに使う**のが主目的 |

### 4-3. 指標セット

**検索の評価（自動・決定的）** — 正解ページを人手で紐づけたゴールデンデータに対して：

- `Recall@k`：正解ページが上位k件に入ったか（**最重要**。ここが取れなければ生成は絶対に正しくならない）
- `MRR`：正解が何位に来たか
- `Context Precision`：取ってきた文脈のうち実際に使えた割合

**生成の評価（LLM-as-a-Judge）**：

- **Faithfulness（忠実性）** — 回答が検索文脈だけで裏付けられるか。**本件の最重要指標**。引き継ぎ資料で嘘をつくのが最悪のシナリオであり、「答えられない」より「間違って答える」方が有害
- **Answer Relevancy** — 質問に答えているか
- **Completeness** — 必要な情報を落としていないか（特に手順型の質問）

**ルールベース（ガードレール）**：

- 出典ページ名が回答に含まれているか
- 代（世代）の取り違えがないか（41代の質問に38代の情報だけで答えていないか）
- 回答不能型の質問に、正しく「Wikiに記載がない」と答えられたか

### 4-4. ゴールデンデータセット設計

**50〜80問**。現役部員・OBに「新入生から実際に聞かれること」を出してもらうのが最良。質問種別でラベル分けし、種別ごとに精度を見る（全体平均では改善点が見えない）：

| 種別 | 目安 | 例 |
|---|---|---|
| 事実検索型 | 20問 | 「大利根飛行場の予約方法は？」 |
| 手順型 | 15問 | 「トラックの積み込み手順は？」 |
| 比較・横断型 | 15問 | 「40代と41代の空力設計の違いは？」 |
| 全域型 | 10問 | 「歴代の駆動系の課題の変遷は？」 |
| **回答不能型** | 10問 | 「来年度の予算は？」（Wikiにない情報。**ハルシネーション検出用**） |

### 4-5. 運用

- 検索評価：CIで毎回自動実行（数秒・無料）
- LLM判定：変更時に全問実行（80問×3指標で数百円）
- 人手評価：月1回20問。**LLM判定との一致率を測り、判定器自体を検証する**

## 5. 精度改善手法

効果の大きい順に並べる。**データ品質がプロンプトより効く**というのが本件の見立て。

### 5-1. データ品質（最優先）

| 施策 | 内容 | 効果 |
|---|---|---|
| **パンくず付与** | 各チャンクに `ページ名 > H2 > H3` を埋め込む | ★★★ 検索精度に最も効く。「駆動設計 > 3. ギア比 > 選定理由」の文脈が乗るだけで別物になる |
| **階層マージ** | 節の中央値が191字と細かすぎる。H3/H4を親H2の下に**1000〜2000字になるまで結合** | ★★★ 文脈の断絶を防ぐ |
| **代・班のメタデータ付与** | タイトルから正規表現で抽出（`(41st)`、`38th`）＋抽出できない無印ページはLLMで補完（117回、$1程度） | ★★★ 決定的フィルタが可能になる |
| **用語集の構築** | TF・鳥コン・桁・リブ・プラホ・スパー・ペラ 等のサークル内略語 | ★★★ 検索とプロンプト両方に効く。**新入生の質問は略語を知らない前提で来る** |
| **表のMarkdown変換** | wikitableの39個をMarkdown表へ | ★★ LLMの表読解精度が上がる |
| **画像キャプション抽出** | `[[ファイル:x.png\|thumb\|主翼桁の断面]]` のキャプションを本文に残す | ★★ 図の情報が本文から失われるのを防ぐ |
| **スタブ除外** | 200字未満38ページを検索対象から外す | ★ ノイズ削減 |
| **リンク構造の活用** | 内部リンク267本を関連ページ推薦に使う | ★ |

### 5-2. データローダー

**wikitext直処理で行く**（テンプレートが実質ゼロと判明したため）。除去・変換対象：

- `[[記事名|表示名]]` → 表示名（リンク先はメタデータに退避）
- `[[ファイル:...|thumb|キャプション]]` → キャプションを残し画像URLを退避
- `{| ... |}` → Markdown表
- `'''強調'''` `''斜体''` → Markdown
- 外部リンク287本 → URLは保持（参考資料として価値がある）

**検証項目（PoCで実測する）**：wikitext直 vs `action=parse`のHTML→Markdown変換で、検索精度に差が出るか。今の見立てでは差は小さいが、実測で確認する。

### 5-3. 検索手法

| 手法 | 採否 | 理由 |
|---|---|---|
| **メタデータ事前フィルタ** | ✅ 最優先 | 「41代の」と言われたら代で絞る。ベクトル検索より確実で速い |
| **BM25 + ベクトルのハイブリッド** | ✅ | 部品名・人名・機体名などの固有名詞はBM25が強い。日本語形態素解析は SudachiPy を想定 |
| **親子チャンク（Parent Document Retriever）** | ✅ | 節単位で検索 → ヒットしたら親ページ全体（または前後の節）を渡す。§5-1の階層マージと合わせて文脈切れ対策 |
| **リランキング** | ✅ | Top-20を広く取り、Claudeまたはリランカーで上位5件に絞る |
| **クエリ書き換え・拡張** | ✅ | 用語集を使い「ペラ」→「プロペラ」、「桁」→「主桁 スパー」等に展開 |
| **HyDE**（仮想回答による検索） | △ 保留 | 効果はあるがレイテンシ増。ベースラインで不足なら検討 |

### 5-4. プロンプト品質

- **出典の強制**：「回答には必ず参照したページ名と最終更新日を示す」
- **代の明示**：「どの代の情報かを明示する。無印ページは代不明として扱う」
- **不知の許容**：「Wikiに記載がなければ、推測せず『記載がない』と答える」— 引き継ぎ資料では**ハルシネーションが最大の害**であり、これを最優先の制約に置く
- **鮮度の警告**：「参照元が2年以上前なら、情報が古い可能性を添える」

## 6. 決定事項（壁打ち済み）

| 論点 | 決定 | 根拠 |
|---|---|---|
| **設置形態** | **Webアプリ**（Discord等のチャット連携は不採用） | WASA全体のDiscordは存在せず、**代ごとのDiscordしかない**。代を超えて引き継ぐためのツールが、代ごとに消える場所にあるのは構造的に矛盾する |
| **アクセス制御** | **共有パスワード1本**（Cookieセッション） | URL限定公開は認証ではない。Wikiは意図的に非公開であり、その判断をしたのは本プロジェクトの担当者ではない。共有パスワードなら実装1時間・依存ゼロで、リスクを桁で下げられる。Wikiのパスワードとは別物にする |
| **保守の主体** | 当面は開発者本人。API費用も個人負担 | 月100質問で¥1,000〜2,000程度と試算。ただし**READMEに「壊れたときの直し方」を最初から書く**方針は維持する |
| **バックエンド** | **Go** | 学習目的が明示されており、用途との相性も良い（公式SDKあり・単一バイナリ・goroutineで要約の並列生成・kagomeで日本語形態素解析が完結） |
| **フロントエンド** | **TypeScript + React（Vite / SPA）** | Next.jsはBFF層を内包するため、Goでバックエンドを分離する意図と役割が重複する。純SPAの方が境界がきれい |
| **オフライン処理・評価** | **Python** | 既存の `dump_wiki.py` を活かす。評価の集計・可視化はPythonが圧倒的に速い。本番に載らないコードなので言語統一の価値が薄い |
| **データストア** | **なし（JSONファイル）** | 117ページ・30万字。目次も要約もチャンクもJSON 1個（数MB）に収まる。DBもベクトルDBも立てない |
| **ホスティング** | Google Cloud Run 想定 | アイドル時ゼロスケール。この規模なら無料枠内。サーバー代は実質¥0でAPI従量課金のみ |

### 埋め込み（ベクトル検索）を使う場合の役割分担

Goは埋め込みモデルのローカル実行が苦手だが、設計で回避する。

- **生成**：Python側でオフラインに実行し、ベクトルをJSONに焼き込む
- **検索**：Goは内積を計算するだけ。数百チャンク規模なら総当たりで一瞬

GoにMLライブラリを持ち込む必要はない。

### デプロイ構成

Goの `embed` でビルド済みSPAをバイナリに同梱する。

- **開発時**：Vite dev server + プロキシで分離したまま作業
- **本番**：バイナリ1個。CORS設定不要、デプロイ先1つ

分離して作り込みつつ、運用は単純なまま保てる。
