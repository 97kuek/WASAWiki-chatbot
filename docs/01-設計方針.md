# WASA Chat 設計方針（検討メモ v0.3）

この文書は、WASA Chatが**なぜいまの形になっているのか**をまとめたものです。

作り方そのものではなく、「なぜこの方式を選び、なぜ別の方式を捨てたのか」を書いています。
引き継いだ人が同じ検討を最初からやり直さずに済むように、そして
一度捨てた案をうっかり蒸し返さずに済むように残しています。

ここに書かれた判断は、ほとんどが**実際に測った数字から決めたもの**です。
なので、異論があるときは「なんとなく良さそう」ではなく、その数字に反論する形でお願いします。

> 状態: **初期Webアプリ実装済み・精度検証／本番準備フェーズ**。実測値に基づいて更新している。
> v0.2でCodexによるレビュー指摘を反映し、v0.1にあった矛盾（3箇所）を解消した。§10参照。

## 0. 前提となる実測値

設計の話をする前に、扱うデータがどれくらいの規模なのかを見ておきましょう。

**この数字がすべての判断の出発点になっています。** 例えば「ページ数が数万あるのか、
数百なのか」で、必要な仕組みはまったく変わります。WASA Chatの場合は後者でした。

以下は`dump_wiki.py`と`build_index.py`の実行結果です。

| 項目 | 実測 | 設計への含意 |
|---|---|---|
| 本文ページ数 | 117（うちリダイレクト3、実記事114） | **極小**。分散DBもスケール設計も不要 |
| 総文字数 | 296,933字 | 現行マスキング・整形後。全文で20〜30万トークン規模 |
| 検索対象ページ | 104（実記事114のうち） | 20字未満だけチャンク化せず、短いページも検索対象に残す |
| チャンク数 | 349（中央値843字 / 最大2431字） | 2026-08-09の現行索引。節の中央値は191字と細かすぎるため、階層マージ後の値 |
| 見出し数 | 865（H2:231 / H3:326 / H4:223 / H5:65 / H6:20） | 階層構造が明確。パンくずの精度が高い |
| 表（wikitable） | 39個 | 少ない。rowspan/colspanは未対応のまま許容 |
| テンプレート | **実質0**（DISPLAYTITLE/DEFAULTSORTのみ4件） | `action=parse`でのHTML化が不要。wikitext直で読める |
| 画像 | 67枚（PNG41・JPEG26）/ 本文参照57箇所 | キャプションが情報を持つ。必要性はM21で測定済み |
| 更新の生存性 | 117中68ページが2025〜2026年更新 | 生きたWiki。更新追随の設計が必須 |

### 公式サイト（v0.3で追加、`dump_site.py`）

途中で、Wikiだけでは足りないことが分かりました。

引き継ぎWikiは「作り方」にはとても詳しいのですが、**団体の成り立ちや歴代機体といった
対外的な説明がありません。** そのため「WASAとはどんなサークルか」「歴代の機体名と記録は」
といった質問に答えられませんでした。

そこで、一般公開されている https://wasa-birdman.com/ も取り込むことにしました。

| 項目 | 実測 | 備考 |
|---|---|---|
| 固定ページ | 31（本文80字未満の9件は除外） | 団体紹介・班紹介・機体一覧・年間の活動サイクル |
| 投稿（活動報告） | 479 | 2011〜2026年の試験飛行報告など。1件平均753字 |
| 取得時の総文字数 | 384,194字 | 短いページの除外と整形後、索引に入る本文は349,923字。**Wiki本文（300,425字）より多い** |
| 取得経路 | sitemap索引 → post/page-sitemap | WP REST APIは無効（`/wp-json/`が404）。`<loc>`はCDATA包み |
| ページ構成 | Elementor製。`entry-content`が無い | `data-elementor-type="wp-page"`を本文とみなす |
| robots.txt | `search=yes, ai-train=no, use=reference` | 出典リンク付きの参照は許可。学習には使わない |

2つの出所は`index.json`の`source`で区別しています（`wiki` / `site`）。

回答プロンプトでは「両方に書いてあって食い違う場合は引き継ぎWikiを優先」と指示し、
画面の出典にもどちらから引いたかを表示しています。これは見た目の問題ではなく、
**その情報を部外に出してよいかどうかの判断に必要**だからです。

### ここから導かれる基本認識

以上の数字から、次の3つが言えます。

1. **データが想定以上にきれいです。** テンプレートが実質ゼロなので、wikitextを直接扱えます
2. **規模が小さいです。** ベクトルDBのインフラを組むより、全件をメモリに載せて
   総当たりする方が速く、正確で、安く済みます
3. **構造化のヒントが既にあります**（`空力設計(41st)`、`構造設計 38th`）。
   ただし、タイトルに代が入っているのは114ページ中26ページだけなので、
   機械抽出だけでは足りません（§6-2）

## 1. RAG方式の選定：ドキュメント / SQL / グラフ

RAGにはいくつかの方式があります。まずどれを土台にするかを決めました。

| 方式 | 本件での強み | 本件での弱み | 判定 |
|---|---|---|---|
| **ドキュメントRAG** | 本文の大半が非構造の散文・箇条書き。素直に効く | 全域質問に原理的に弱い | **主軸として採用** |
| **SQL RAG** | 属性クエリ・集計・並べ替えに強い。決定的で検証しやすい | 対象となる構造化DBが存在しない | **限定採用**（メタデータ層のみ） |
| **グラフRAG** | 「代 × 班 × 部品 × 人」の関係と相性は良い | 構築コストが規模に見合わない | **不採用** |

### 結論：ドキュメントRAG主軸 + 軽量メタデータ層

グラフRAGは魅力的に見えるので、見送った理由を書いておきます。

GraphRAGの主な価値は、**コミュニティ要約による全域質問への対応**であって、
グラフ構造そのものではありません。本件では、その価値の相当部分を
階層的な事前要約（§3）で安く得られます。117ページという規模では、
グラフを組むコストが便益を上回ると判断しました。

> ⚠️ v0.1では「階層的要約はGraphRAGと機能的に等価」と書いていましたが、
> **これは言い過ぎだったので撤回します。** 事前要約には
> 「要約時に落とした情報は永久に取り出せない」という弱点があり、
> グラフ探索による動的な関係発見とは等価ではありません。
> 全域質問への実用的な近似、という位置づけが正確です。

SQL RAGは、利点だけを限定採用しています。Text-to-SQLはやらず、
ページ属性をテーブルの形で持つだけです。

```
pages(id, title, aliases, 代, 代の根拠, 班, categories, 最終更新, revid, 文字数, is_stub, 要約)
chunks(id, page_id, パンくず, 本文, 文字数)
images(file, キャプション, 掲載ページ)
links(from_page, to_page)      -- 内部リンクから自動構築
```

これだけで「41代の資料一覧」「電装班の全ページ」「今年更新されたページ」は、
検索を経由せずに確実へ答えられます。

## 2. アーキテクチャ（段階的に足す）

**重要な方針です。以下の層を、初期版から全部入れないでください。**

RAGの解説記事にはたくさんの層が出てきますが、全部入れると何が効いているのか
分からなくなりますし、費用も待ち時間も増えます。各層は、
**前段の実測で不足が確認できたときにだけ**追加します。

```
Phase 1（まずここだけ作る）
├ L0 メタデータ層（JSON）      代・班・更新日で決定的にフィルタ
├ L1 目次層（常時コンテキスト）  全114ページのタイトル＋要約＋更新日（1〜2万トークン）
└ L3 本文層（ツール経由）       get_page / get_chunk で全文を渡す

Phase 2（L1で足りないと測れたら）
└ L2 検索層                    BM25（+ 必要ならベクトル）、メタデータで事前フィルタ

Phase 3（全域質問が実際に来ると分かったら）
└ L4 要約層                    ページ要約 → 班・代別要約 → 全体要約

Phase 4（測って効果が出たものだけ）
└ 質問ルーター / クエリ書き換え / リランキング
```

**この設計の肝は、L1（目次を常時コンテキストに置く）です。**

114ページという規模だからこそ、目次全体が1〜2万トークンに収まります。
つまりモデルは常にWiki全体の見取り図を持った状態で、必要なページだけを取りに行けます。
検索が多少失敗しても致命傷になりません。

### 形態素解析器はkagomeに一本化する

⚠️ ここは事故が起きやすい箇所なので明記しておきます。

**索引側（Python/SudachiPy）と検索側（Go/kagome）で分かち書きが食い違うと、BM25は壊れます。**
同じ文章が違う単語に分割されるので、一致するはずのものが一致しなくなります。

そこで、BM25の索引構築・検索の両方をGo側でkagomeを使って行います。
Python側のパイプラインは形態素解析を行いません。

### ベクトル検索を使う場合（Phase 2以降・要検証）

もし将来ベクトル検索を足すなら、次の形にします。

- **埋め込み生成**: Python側でオフラインに実行し、ベクトルをJSONに焼き込みます
- **質問の埋め込み**: Go側から同一モデルのAPIを呼びます（索引と検索でモデルが一致することが必須です）
- **検索**: Goは内積を計算するだけです。数百チャンク規模なら総当たりで一瞬です

この形にすれば、GoにMLライブラリを持ち込む必要はありません。

## 3. 全域的タスクへの対応

Top-k検索型のRAGには、原理的に答えられない質問があります。

「歴代で駆動系のトラブルはどう変遷した？」「うちのサークルの設計思想を要約して」
のような、**全体を見ないと答えられない質問**です。上位5件を取ってくる方式では、
そもそも全体を見ていないので答えようがありません。

対応方法は3つ検討しました。

| 手法 | 評価 |
|---|---|
| **MapReduce** | 正確。114回のAPI呼び出しは1回$1程度で許容範囲。ただしリアルタイムでは遅い |
| **Refine** | **不採用**。114件は長すぎ、順序依存で初期の情報が薄れる。10件程度までの手法 |
| **階層的事前要約** | **採用**。MapReduceの結果をキャッシュする。全域質問が即答になる |

採用した階層的事前要約は、次の構成です。

```
L4-a  ページ要約     114個  （各200字）  = 約2.3万字
L4-b  班別・代別要約   ~15個 （各600字）  = 約0.9万字
L4-c  全体要約         1個   （1500字）
```

合計で約3.5万字（〜3万トークン）です。丸ごとコンテキストに入れても安く済みます。

更新への追随は、`list=recentchanges`と`revid`の比較で変更ページを検出し、
そのページの要約だけを再計算 → 属する班・代の要約 → 全体要約、と差分更新します。

## 4. RIG（Retrieval Interleaved Generation）の採否

### 判定：**不採用**

理由は3つあります。

1. **そもそも前提が違います。** RIGの本領は、権威ある統計DBと照合して数値を検証することです。
   本件には照合先の正解DBが存在しません。数値（翼幅・重量・出力）はWiki本文に散在していて、
   それ自体が検索対象であって、検証の基盤ではありません
2. **ツール呼び出しループが実質的に上位互換です。** 生成中に「このページを読む必要がある」と
   判断してツールを呼ぶ挙動は、interleaved retrievalそのものです
3. **実装コストが便益に見合いません**

ただし、**検証可能性という思想は取り込んでいます。** 回答に使ったページは
サーバーが索引から出典カードとして表示し、モデルに出典名やURLを作らせません。
回答本文が資料で裏付けられるかどうかは、§5のFaithfulnessで検査します。

## 5. 精度評価アプローチ

### 5-1. 評価は「検索」と「生成」の2層に分離する

これは最初に決めておくべきことでした。

混ぜて測ると、精度が悪かったときに**検索が悪いのか生成が悪いのか切り分けられず、
改善のループが回りません。** 実際、この分離があったおかげで
「正しいページを選んでいるのに記載なしと答える」という失敗を特定できました。

### 5-2. 手法の採否

| アプローチ | 採否 | 理由 |
|---|---|---|
| **BLEU / ROUGE** | ❌ **不採用** | 日本語のn-gram一致は分かち書き依存で不安定。RAG回答は「同じ意味・違う表現」が常態。参照回答を書くコストの割にLLM判定との相関が低い。**測っても改善に繋がらない指標は入れない** |
| **埋め込みベース** | △ **補助のみ** | 「意味は近いが事実が誤り」を検出できない。回帰検知（前回との差分監視）にだけ使う |
| **ルールベース** | ✅ **採用** | 安く決定的。ガードレールとして必須 |
| **LLM-as-a-Judge** | ✅ **主軸** | RAG評価の現実解。1問数円 |
| **人手評価** | ✅ **採用（少量・定期）** | 唯一の真の正解。**LLM判定器のキャリブレーションが主目的** |

### 5-3. 指標セット

**検索の評価（自動・決定的）**

- **Evidence Recall@k（節単位）**
  - ⚠️ ページ単位のRecallでは不十分です。**36,443字ある「駆動・フレーム班」がヒットしても、
    正解の節が取れているとは限りません。** そのためゴールデンデータには
    「どのチャンクが根拠か」まで紐づけています
- **all-evidence recall / nDCG**
  - 複数の資料が必要な質問には、MRR（最初の正解の順位）ではなく
    「必要な根拠を全部取れたか」を見ます
- **Context Precision**
  - 取ってきた文脈のうち、実際に使えた割合です

**生成の評価（LLM-as-a-Judge）**

- **Faithfulness（忠実性）**
  - 回答が検索文脈だけで裏付けられるかです。**本件の最重要指標**にしています
  - 引き継ぎ資料では、「答えられない」より「間違って答える」方がはるかに有害だからです
- **Answer Relevancy**: 質問に答えているか
- **Completeness**: 必要な情報を落としていないか（特に手順型）

**Oracle-context評価（切り分け用）**

正解チャンクを直接渡した状態で、生成だけを評価します。
これで「検索が悪いのか生成が悪いのか」が確定します。

**判定器そのものの検証**

判定器を無条件に信じないことも決めています。

- LLM Judgeの**false-accept率**（誤りを正しいと判定してしまう率）
- 人手評価との**Cohen's κ**（一致度）。κが低ければ、判定器の指標としては使えません

**ルールベース（ガードレール）**

- 出典カードが、索引に実在するページだけで組み立てられているか
- 代（世代）の取り違えがないか
- 回答不能型の質問に、正しく「Wikiに記載がない」と答えられたか

### 5-4. ゴールデンデータセット

**Phase 1では30問**とします（ベースライン測定用の最小構成）。
Phase 2以降で50〜80問に拡張します。

| 種別 | Phase 1 | 例 |
|---|---|---|
| 事実検索型 | 10問 | 「大利根飛行場の予約方法は？」 |
| 手順型 | 7問 | 「トラックの積み込み手順は？」 |
| 比較・横断型 | 7問 | 「40代と41代の空力設計の違いは？」 |
| 全域型 | 3問 | 「歴代の駆動系の課題の変遷は？」 |
| **回答不能型** | 3問 | 「来年度の予算は？」（**ハルシネーション検出用。削らない**） |

各問には「正解チャンクID」を紐づけます（Evidence Recallの算出に必須です）。

### 5-5. 運用

- 検索評価: CIで毎回自動実行します（数秒・無料）
- LLM判定: 変更時に全問実行します（30問×3指標で数百円）
- 人手評価: 月1回20問。**LLM判定との一致率（κ）を測り、判定器自体を検証します**

## 6. 精度改善手法

効果の大きい順に並べています。

本件での見立ては、**データ品質がプロンプトより効く**というものです。
これは実際に裏付けが取れました。目次のリード文を直しただけで、
パラメータ数が10倍以上違うモデルの差が消えています（M4）。

### 6-1. データ品質（実装済みのものを含む）

| 施策 | 状態 | 効果 |
|---|---|---|
| **パンくず付与**（ページ名 > H2 > H3） | ✅ 実装済 | ★★★ 検索精度に最も効く |
| **階層マージ**（節191字 → 中央値867字） | ✅ 実装済 | ★★★ 文脈の断絶を防ぐ |
| **最上位見出しをまたぐ結合の抑制** | ✅ 実装済 | ★★ ただし小グループ同士は結合を許す（厳格にすると細切れになる） |
| **用語集の構築**（TF・鳥コン・桁・リブ・プラホ・ペラ） | ⏳ 未着手 | ★★★ 検索とプロンプト両方に効く。**新入生は略語を知らない前提で質問する** |
| **代・班のメタデータ付与** | △ 部分的（§6-2） | ★★★ 決定的フィルタの前提 |
| **表のMarkdown変換** | ✅ 実装済（rowspan未対応） | ★★ |
| **画像キャプション抽出** | ✅ 実装済（M21で日本語パラメータの取りこぼしを修正） | ★★ 図の情報が失われるのを防ぐ |
| **リダイレクトを別名として保持** | ✅ 実装済（3件） | ★★ 別名で検索されても引ける |
| **スタブを目次に残し検索から外す** | ✅ 実装済（25件） | ★ 「存在は知らせる、中身は無い」 |
| **カテゴリの保持** | ✅ 実装済 | ★ |
| **`<nowiki>`/`<code>`/`<pre>`の保護** | ✅ 実装済 | ★ 中のマークアップが壊れるのを防ぐ |

### 6-2. 代（世代）の抽出 — 想定より難しい

実測は**タイトル由来26 / 本文由来23 / 不明65**（114ページ中）でした。

タイトルからのルール抽出だけでは23%しか埋まりません。本文スキャンを足して43%です。
根拠の強さが違うので、`gen_source`で区別しています（タイトル由来＝確定、本文由来＝推定）。

> **ここで重要な気づきがありました。不明65件のすべてが抽出失敗ではありません。**
> 「ESP32のGPIOについて」「トラックの積み込み」のように、
> **そもそも代に依存しない知識のページ**が相当数あります。
>
> したがってLLM補完のタスクは「代を当てる」ではなく、
> **「代依存か、代非依存かを分類し、代依存なら代を推定する」**ことになります。

### 6-3. データローダー

テンプレートが実質ゼロなので、wikitextを直接処理しています。

> ⚠️ v0.1にあった「wikitext直 vs HTML経由のA/B検証」は、**不要と判明したため取り下げました。**

未対応のまま許容しているものが2つあります。表のrowspan/colspanと、
チャンクのオーバーラップです（後者は親子チャンクで代替する想定で、Phase 2で要検証）。

### 6-4. 検索手法（Phase 2）

| 手法 | 採否 |

### 費用方針（API以外はゼロ）

学生サークルのツールなので、費用は最初から設計に入れています。

| 項目 | 費用 |
|---|---|
| Cloudflare Pages | ¥0（帯域・リクエスト無制限、`*.pages.dev`でドメイン購入も不要） |

**請求事故の防止（必須）**

無料枠は、設定を1つ間違えるだけで簡単に超えます。次の6つは必ず守ってください。

1. `min-instances = 0`を維持します（`1`にすると無料枠を確実に超えます）
2. 初期運用は`max-instances = 1`にします（Geminiの送信間隔と停止状態をプロセス内で
   共有しているためです。2台以上にする前に、外部の共有制限が必要になります）
3. 予算アラートを¥1で設定します
4. **Go側に利用者単位のレート制限を入れます**（利用者1人あたり1日30質問程度）。
   HMAC化した利用者キーでFirestoreの回数を原子的に確保し、
   別端末や再起動でリセットされないようにします
5. **Gemini利用時はプロジェクト全体でも制御します。** 呼び出しを直列化して4秒以上空け、
   短時間の429 / 503は最大2回だけ再試行します。短時間上限は1〜15分、
   日次上限は再試行せず太平洋時間0時まで停止し、無駄な再送を防ぎます
6. **Geminiのデータ利用条件を組織で承認してから使います。** 2026-08-08のWASA会議で、
   代表・PMが非公開Wiki本文の無料枠への送信を許可しました。本番は、有料枠なら
   `GEMINI_PAID_TIER=true`、今回承認された無料枠なら`GEMINI_FREE_TIER_APPROVED=true`を
   明示した場合だけ起動します

**API費用の削減**

プロンプトキャッシュ（1時間TTL）と、段階別のモデル選択を使います。

画面ではプロバイダ固有の名前ではなく「自動・じっくり」の2択だけを見せ、

M2b-2で、ページ選択には判断力が必要だが、回答の出典形式は軽量モデルでも31/31で

## 8. 認証と残る未決事項

### 8-1. 認証：Wikiアカウント連携（決定済み・v0.3で共有パスワードから変更）

ここは一度作り直した箇所なので、経緯も含めて書いておきます。

**当初は共有パスワード1本でした。** 実装は1時間で済んだのですが、
運用に載せる前に致命的な欠点が出ました。

- 誰が使ったか分からない（**監査できない**）
- 退部者を個別に締め出せない（**失効できない**）
- **利用者を区別できず、レート制限や将来の監査を個人単位にできない**

決め手は3つ目でした。費用の安全弁を利用者単位にする必要があり、
そのためには誰が使っているかを識別できなければなりません。

**採用した方式**は、ログインフォームで受け取った利用者名とパスワードを、
バックエンドが対象Wikiの`action=clientlogin`にそのまま中継し、
`status: PASS`なら正規化された利用者名を載せた署名付きCookieを発行する、というものです。

| 論点 | 評価 |
|---|---|
| 新しいパスワードの配布 | **不要**。全員すでにWikiのアカウントを持っている |
| 失効 | **Wiki側でアカウントを止めるだけ**。こちら側の作業ゼロ |
| 個人の識別 | 利用者名が取れる。レート制限の按分に使える |
| 費用 | ¥0。外部IDプロバイダも独自ドメインも要らない |
| Wiki管理者の協力 | **不要**。APIを叩くだけで、設定変更を頼む必要がない |

⚠️ **ただし代償があります。アプリがWikiのパスワードを一度受け取る中継点になります。**

これは軽い話ではないので、譲れない前提を3つ置いています。

1. パスワードは**保存しない・ログに出さない**。検証に使って即座に捨てます（`internal/wiki/auth.go`）
2. Cookieに載せるのは**利用者名と有効期限だけ**。HMAC署名し、HttpOnly / Secureを付けます
3. **HTTPS必須**。フロントを別オリジンに置くため`SameSite=None`になり、Secureが前提になります

あわせて、次も守ります。

- 認証経路は、通常アカウントの`action=clientlogin`だけに統一します
- BotPasswords用の旧`action=login`分岐は持ちません
- 画面には、WASA Wikiの利用者名とパスワードだけを入力させます
- パスワードをアプリへ渡すこと自体の是非を見直す場合は、別の認証方式として改めて検討します

**Cloudflare Accessを採らなかった理由**も書いておきます。独自ドメインが前提で
年1,000〜2,000円かかり、「API以外は¥0」と衝突します。加えて部員のメールアドレス一覧を
別途管理する必要があり、**Wikiのアカウント一覧というすでにある名簿**を
二重管理することになるためです。
