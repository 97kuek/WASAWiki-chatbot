`dump_wiki.py` と `build_index.py` の実行結果。設計判断はすべてこの数字に紐づく。

### ここから導かれる基本認識

1. **データが想定以上にきれい**。テンプレートが実質ゼロなので wikitext を直接扱える。
2. **規模が小さい**。ベクトルDBのインフラを組むより、全件をメモリに載せて総当たりする方が速く正確で安い。
3. **構造化のヒントが既にある**（`空力設計(41st)`、`構造設計 38th`）。ただし**タイトルに代が入っているのは114ページ中26ページだけ**で、機械抽出だけでは足りない（§6-2）。

## 1. RAG方式の選定：ドキュメント / SQL / グラフ

| 方式 | 本件での強み | 本件での弱み | 判定 |
|---|---|---|---|
| **ドキュメントRAG** | 本文の大半が非構造の散文・箇条書き。素直に効く | 全域質問に原理的に弱い | **主軸として採用** |
| **SQL RAG** | 属性クエリ・集計・並べ替えに強い。決定的で検証しやすい | 対象となる構造化DBが存在しない | **限定採用**（メタデータ層のみ） |
| **グラフRAG** | 「代 × 班 × 部品 × 人」の関係と相性は良い | 構築コストが規模に見合わない | **不採用** |

### 結論：ドキュメントRAG主軸 + 軽量メタデータ層

グラフRAGを見送る根拠。GraphRAGの主要な価値は**コミュニティ要約による全域質問への対応**であり、グラフ構造そのものではない。本件ではその価値の**相当部分**を階層的な事前要約（§3）で安く得られる。117ページの規模では、グラフを組むコストが便益を上回る。

> ⚠️ v0.1 では「階層的要約はGraphRAGと機能的に等価」と書いたが、**言い過ぎだったので撤回する**。事前要約は「要約時に落とした情報は永久に取り出せない」という弱点を持ち、グラフ探索による動的な関係発見とは等価ではない。全域質問への実用的な近似、という位置づけが正確。

SQL RAGは利点だけ限定採用する。Text-to-SQLはやらず、ページ属性をテーブル化する：

```
pages(id, title, aliases, 代, 代の根拠, 班, categories, 最終更新, revid, 文字数, is_stub, 要約)
chunks(id, page_id, パンくず, 本文, 文字数)
images(file, キャプション, 掲載ページ)
links(from_page, to_page)      -- 内部リンクから自動構築
```

これで「41代の資料一覧」「電装班の全ページ」「今年更新されたページ」は、検索を経由せず確実に答えられる。

## 2. アーキテクチャ（段階的に足す）

**重要：以下を初期版から全部入れない。** 各層は前段の実測で不足が確認できたときにだけ追加する。

```
Phase 1（まずここだけ作る）
├ L0 メタデータ層（JSON）      代・班・更新日で決定的にフィルタ
├ L1 目次層（常時コンテキスト）  全114ページのタイトル＋要約＋更新日（1〜2万トークン）
└ L3 本文層（ツール経由）       get_page / get_chunk で全文を渡す

Phase 2（L1で足りないと測れたら）
└ L2 検索層                    BM25（+ 必要ならベクトル）、メタデータで事前フィルタ

Phase 3（全域質問が実際に来ると分かったら）
└ L4 要約層                    ページ要約 → 班・代別要約 → 全体要約

Phase 4（測って効果が出たものだけ）
└ 質問ルーター / クエリ書き換え / リランキング
```

**L1（目次を常時コンテキストに置く）が本設計の肝**。114ページという規模だからこそ目次全体が1〜2万トークンに収まる。Claudeは常にWiki全体の見取り図を持った状態で、必要なページだけを取りに行ける。検索の失敗が致命傷にならない。

### 形態素解析器は kagome に一本化する

⚠️ **索引側（Python/SudachiPy）と検索側（Go/kagome）で分かち書きが食い違うとBM25は壊れる。** BM25の索引構築・検索の両方をGo側で kagome を使って行う。Python側のパイプラインは形態素解析を行わない。

### ベクトル検索を使う場合（Phase 2以降・要検証）

- **埋め込み生成**：Python側でオフラインに実行し、ベクトルをJSONに焼き込む
- **質問の埋め込み**：Go側から同一モデルのAPIを呼ぶ（索引と検索でモデルが一致することが必須）
- **検索**：Goは内積を計算するだけ。数百チャンク規模なら総当たりで一瞬

GoにMLライブラリを持ち込む必要はない。

## 3. 全域的タスクへの対応

Top-k検索型のRAGは「全体を見ないと答えられない質問」に原理的に答えられない。想定例：「歴代で駆動系のトラブルはどう変遷した？」「うちのサークルの設計思想を要約して」。

| 手法 | 評価 |
|---|---|
| **MapReduce** | 正確。114回のAPI呼び出しは1回$1程度で許容範囲。ただしリアルタイムでは遅い |
| **Refine** | **不採用**。114件は長すぎ、順序依存で初期の情報が薄れる。10件程度までの手法 |
| **階層的事前要約** | **採用**。MapReduceの結果をキャッシュする。全域質問が即答になる |

```
L4-a  ページ要約     114個  （各200字）  = 約2.3万字
L4-b  班別・代別要約   ~15個 （各600字）  = 約0.9万字
L4-c  全体要約         1個   （1500字）
```

合計約3.5万字（〜3万トークン）。丸ごとコンテキストに入れても安い。

**更新追随**：`list=recentchanges` と `revid` の比較で変更ページを検出し、そのページの要約だけ再計算 → 属する班・代の要約 → 全体要約、と差分更新する。

## 4. RIG（Retrieval Interleaved Generation）の採否

### 判定：**不採用**

1. **前提が違う**。RIGの本領は権威ある統計DBと照合して数値を検証すること。本件には照合先の正解DBが存在しない。数値（翼幅・重量・出力）はWiki本文に散在しており、それ自体が検索対象であって検証基盤ではない。
2. **ツール呼び出しループが実質的に上位互換**。生成中に「このページを読む必要がある」と判断してツールを呼ぶ挙動は interleaved retrieval そのもの。
3. **実装コストが便益に見合わない**。

ただし**検証可能性という思想は取り込む**。数値・固有名詞を答える際は出典ページ名と該当節を必ず併記させ、出典が示せない主張は出力しない（§5のFaithfulnessで機械的に検出）。

## 5. 精度評価アプローチ

### 5-1. 評価は「検索」と「生成」の2層に分離する

混ぜると、精度が悪いときに検索が悪いのか生成が悪いのか切り分けられず、改善ループが回らない。

### 5-2. 手法の採否

| アプローチ | 採否 | 理由 |
|---|---|---|
| **BLEU / ROUGE** | ❌ **不採用** | 日本語のn-gram一致は分かち書き依存で不安定。RAG回答は「同じ意味・違う表現」が常態。参照回答を書くコストの割にLLM判定との相関が低い。**測っても改善に繋がらない指標は入れない** |
| **埋め込みベース** | △ **補助のみ** | 「意味は近いが事実が誤り」を検出できない。回帰検知（前回との差分監視）にだけ使う |
| **ルールベース** | ✅ **採用** | 安く決定的。ガードレールとして必須 |
| **LLM-as-a-Judge** | ✅ **主軸** | RAG評価の現実解。1問数円 |
| **人手評価** | ✅ **採用（少量・定期）** | 唯一の真の正解。**LLM判定器のキャリブレーションが主目的** |

### 5-3. 指標セット

**検索の評価（自動・決定的）**

- **Evidence Recall@k（節単位）** — ⚠️ ページ単位のRecallでは不十分。**36,443字ある「駆動・フレーム班」がヒットしても、正解の節が取れているとは限らない**。ゴールデンデータには「どのチャンクが根拠か」まで紐づける
- **all-evidence recall / nDCG** — 複数資料が必要な質問には、MRR（最初の正解の順位）ではなく「必要な根拠を全部取れたか」を見る
- **Context Precision** — 取ってきた文脈のうち実際に使えた割合

**生成の評価（LLM-as-a-Judge）**

- **Faithfulness（忠実性）** — 回答が検索文脈だけで裏付けられるか。**本件の最重要指標**。引き継ぎ資料では「答えられない」より「間違って答える」方が有害
- **Answer Relevancy** — 質問に答えているか
- **Completeness** — 必要な情報を落としていないか（特に手順型）

**Oracle-context評価（切り分け用）**

正解チャンクを直接渡した状態で生成だけを評価する。これで「検索が悪いのか生成が悪いのか」が確定する。

**判定器そのものの検証**

- LLM Judge の **false-accept率**（誤りを正しいと判定する率）
- 人手評価との **Cohen's κ**（一致度）。κが低ければ判定器の指標として使えない

**ルールベース（ガードレール）**

- 出典ページ名が回答に含まれているか
- 代（世代）の取り違えがないか
- 回答不能型の質問に、正しく「Wikiに記載がない」と答えられたか

### 5-4. ゴールデンデータセット

**Phase 1では30問**（ベースライン測定用の最小構成）。Phase 2以降で50〜80問に拡張する。

| 種別 | Phase 1 | 例 |
|---|---|---|
| 事実検索型 | 10問 | 「大利根飛行場の予約方法は？」 |
| 手順型 | 7問 | 「トラックの積み込み手順は？」 |
| 比較・横断型 | 7問 | 「40代と41代の空力設計の違いは？」 |
| 全域型 | 3問 | 「歴代の駆動系の課題の変遷は？」 |
| **回答不能型** | 3問 | 「来年度の予算は？」（**ハルシネーション検出用。削らない**） |

各問に「正解チャンクID」を紐づける（Evidence Recallの算出に必須）。

### 5-5. 運用

- 検索評価：CIで毎回自動実行（数秒・無料）
- LLM判定：変更時に全問実行（30問×3指標で数百円）
- 人手評価：月1回20問。**LLM判定との一致率（κ）を測り、判定器自体を検証する**

## 6. 精度改善手法

効果の大きい順。**データ品質がプロンプトより効く**というのが本件の見立て。

### 6-1. データ品質（実装済みのものを含む）

| 施策 | 状態 | 効果 |
|---|---|---|
| **パンくず付与**（ページ名 > H2 > H3） | ✅ 実装済 | ★★★ 検索精度に最も効く |
| **階層マージ**（節191字 → 中央値867字） | ✅ 実装済 | ★★★ 文脈の断絶を防ぐ |
| **最上位見出しをまたぐ結合の抑制** | ✅ 実装済 | ★★ ただし小グループ同士は結合を許す（厳格にすると細切れになる） |
| **用語集の構築**（TF・鳥コン・桁・リブ・プラホ・ペラ） | ⏳ 未着手 | ★★★ 検索とプロンプト両方に効く。**新入生は略語を知らない前提で質問する** |
| **代・班のメタデータ付与** | △ 部分的（§6-2） | ★★★ 決定的フィルタの前提 |
| **表のMarkdown変換** | ✅ 実装済（rowspan未対応） | ★★ |
| **画像キャプション抽出** | ✅ 実装済（57/57） | ★★ 図の情報が失われるのを防ぐ |
| **リダイレクトを別名として保持** | ✅ 実装済（3件） | ★★ 別名で検索されても引ける |
| **スタブを目次に残し検索から外す** | ✅ 実装済（25件） | ★ 「存在は知らせる、中身は無い」 |
| **カテゴリの保持** | ✅ 実装済 | ★ |
| **`<nowiki>`/`<code>`/`<pre>` の保護** | ✅ 実装済 | ★ 中のマークアップが壊れるのを防ぐ |

### 6-2. 代（世代）の抽出 — 想定より難しい

実測：**タイトル由来26 / 本文由来23 / 不明65**（114ページ中）。

タイトルからのルール抽出だけでは23%しか埋まらない。本文スキャンを足して43%。根拠の強さが違うため `gen_source` で区別している（タイトル由来＝確定、本文由来＝推定）。

> **重要な気づき：不明65件のすべてが抽出失敗ではない。** 「ESP32のGPIOについて」「トラックの積み込み」のように、**そもそも代に依存しない知識のページ**が相当数ある。したがってLLM補完のタスクは「代を当てる」ではなく **「代依存か、代非依存か」を分類し、代依存なら代を推定する** ことになる。

### 6-3. データローダー

wikitext直処理（テンプレートが実質ゼロのため）。

> ⚠️ v0.1 にあった「wikitext直 vs HTML経由のA/B検証」は**不要と判明したため取り下げ**。

**未対応として許容しているもの**：表の rowspan/colspan、チャンクのオーバーラップ（親子チャンクで代替する想定。Phase 2で要検証）。

### 6-4. 検索手法（Phase 2）

| 手法 | 採否 |
|---|---|
| **メタデータ事前フィルタ** | ✅ 最優先。ベクトル検索より確実で速い |
| **BM25**（kagome、Go側に一本化） | ✅ 固有名詞に強い |
| **ベクトル検索とのハイブリッド** | △ BM25で不足と測れたら |
| **親子チャンク** | ✅ 節単位で検索 → ヒットしたら親ページを渡す |
| **リランキング** | △ 効果を測ってから |
| **クエリ書き換え・拡張** | △ 用語集ができてから |
| **HyDE** | ❌ 現時点では見送り |

### 6-5. プロンプト品質

- **出典の強制**：参照したページ名と最終更新日を必ず示す
- **代の明示**：どの代の情報かを明示する。代不明のページはその旨を伝える
- **不知の許容**：Wikiに記載がなければ推測せず「記載がない」と答える（**最優先の制約**）
- **鮮度の警告**：参照元が2年以上前なら情報が古い可能性を添える

## 7. 決定事項

| 論点 | 決定 | 根拠 |
|---|---|---|
| **設置形態** | **Webアプリ** | WASA全体のDiscordは存在せず代ごとのDiscordしかない。代を超えて引き継ぐツールが代ごとに消える場所にあるのは矛盾 |
| **アクセス制御** | **共有パスワード1本**（Cookieセッション）。§8-1にトレードオフを記載 | URL限定公開は認証ではない。実装1時間・依存ゼロ・費用ゼロ |
| **保守の主体** | 当面は開発者本人。API費用も個人負担 | READMEに「壊れたときの直し方」を書く方針は維持 |
| **バックエンド** | **Go** | 公式SDKあり・単一バイナリ・goroutineで並列要約・kagomeで形態素解析が完結・**コールドスタートが速い**（Cloud Runのゼロスケールで実際に効く） |
| **フロントエンド** | **TypeScript + React（Vite / SPA）** | Next.jsはBFF層を内包し、Goでバックエンドを分離する意図と重複する |
| **オフライン処理・評価** | **Python** | 既存の `dump_wiki.py` を活かす。評価の集計はPythonが速い |
| **データストア** | **なし（JSONファイル）** | 830KB。DBもベクトルDBも立てない |
| **デプロイ** | **フロント= Cloudflare Pages / バック= Cloud Run（asia-northeast1）** | ⚠️ v0.1 の「Goバイナリに同梱」と矛盾していたため**分離構成で確定**。CORSはGo側10行程度 |
| **更新反映** | **手動 rebuild**（`python dump_wiki.py && python build_index.py`） | ⚠️ v0.1 で「リアルタイム/日次/手動」が混在していたため**手動で確定**。定期バッチは保守コストの源であり、一人保守の方針と噛み合わない |
| **データの公開範囲** | **コードのみpublic。Wiki本文・インデックスはコミットしない** | 非公開Wikiの内容。`dump/` `data/` `.env` を `.gitignore`。デプロイ時もローカルから直接投入しGitHubを経由させない |

### 費用方針（API以外はゼロ）

| 項目 | 費用 |
|---|---|
| Cloudflare Pages | ¥0（帯域・リクエスト無制限、`*.pages.dev` でドメイン購入も不要） |
| Cloud Run | ¥0（無料枠が月180,000〜240,000 vCPU秒。月500質問で使用率3%以下） |
| Artifact Registry | ¥0（0.5GBまで無料。Goのイメージは20MB程度） |
| Claude API | Sonnet 5 で約¥3.5/質問、Opus 5 で約¥9/質問 |

**請求事故の防止（必須）**

1. `min-instances = 0` を維持する（`1` にすると無料枠を確実に超える）
2. `max-instances = 3` 程度に制限する
3. 予算アラートを¥1で設定する
4. **Go側にレート制限を入れる**（1セッション1日30質問程度）— 共有パスワードが漏れた場合、**本当の費用リスクはインフラではなくAPI従量課金**。これが実質的な上限装置になる

**API費用の削減**：プロンプトキャッシュ（1時間TTL）、モデルの使い分け（ページ選定はHaiku、回答はSonnet/Opus）、`effort` を low/medium から試す。**fast mode は単価が2倍のため不採用**（速度が問題になってから再検討）。

## 8. 残る未決事項

### 8-1. 認証：共有パスワード vs Cloudflare Access

共有パスワードは**失効も監査もできない**（誰が使ったか分からない、退部者を個別に締め出せない）。より堅い選択肢は Cloudflare Access（Zero Trust、50ユーザーまで無料、メール認証・監査ログ・個別失効あり）。

⚠️ ただし **Cloudflare Access は独自ドメインが前提**で、**年1,000〜2,000円かかる**。「API以外は¥0」という方針と衝突する。

→ **Phase 1は共有パスワードで進め、運用に載せる段階で再検討する**。トレードオフとして記録しておく。

### 8-2. その他

1. **画像67枚の扱い** — 中身次第。回路図・設計図なら、テキストだけでは答えられない質問が確実に出る（**要サンプル確認**）
2. **答えてはいけない情報の有無** — 個人情報、金銭、非公開の交渉事など。ダンプ内容の確認が必要
3. **Wiki管理者への一報** — 非公開Wikiの内容を外部（Claude API）に送信し別の場所で閲覧可能にする以上、共有は済ませておくべき
4. **MediaWiki 1.37.2 はサポート終了版**（2021年12月リリース）。本プロジェクトの対象外だが、管理者に共有する価値がある
5. **利用場面と頻度** — コスト試算の精度に影響
