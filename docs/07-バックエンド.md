# WASA Chat バックエンド

バックエンド（`backend/`）が担う、認証とデータの扱いをまとめたドキュメントです。

わかりやすくざっくり言うと、**ログイン処理やログイン後の
ユーザーごとの扱いがどのようになっているのかをまとめたもの**です。

WASA Chatは非公開Wikiの中身を扱います。誰でも見られるアプリにするわけにはいきませんし、
かといって新しいパスワードを全員に配るのも現実的ではありません。
そのあたりをどう解決したかも、あわせて書いていきます。

なお、なぜその方式を選んだかという判断の根拠は[01-設計方針.md](01-設計方針.md)、
本番での実際の作業手順は[04-デプロイ手順.md](04-デプロイ手順.md)にあります。

## 認証方式

まず初めに、認証方式から説明します。

WASA Chatは、**独自のアカウントを持っていません。** ログインに使うのは、
普段WASA Wikiで使っている利用者名とパスワードです。

こうしている理由は3つあります。

- 新しいパスワードを配らなくて済むこと
- 退部した人はWiki側でアカウントを止めれば自動的に締め出せること
- 誰が使ったかが分かるので利用者ごとに回数制限をかけられる

ことです。

### 認証の流れ

まず初めに、ログイン画面でユーザーはwikiで使用する「利用者名」と「パスワード」を入力します。

受け取った情報をWikiへそのまま渡して、Wikiに「この人は本物ですか」と聞きに行きます。

具体的には以下のような流れでバックエンドで認証を行なっています。

1. MediaWikiからログイントークンを取得します
2.  同じHTTPセッションで`action=clientlogin`へ中継します
3. `status: PASS`の場合だけ成功とします
4. Wikiが返した、正規化済みの利用者名を使います

また、wikiとの認証処理は20秒で打ち切りという設定になっています。

## パスワード

この方式にはある代償があります。

それは**WASA Chatが、Wikiのパスワードを一度受け取る中継点になる**という点です。

つまり、部外秘のデータを閲覧できるwikiのパスワードをこのWASA chatが経由しているということです。

そこで、次の扱いを絶対の前提としています。

- 保存しない
- ログへ出さない
- Wikiへの検証が終わったら、保持しない
- Cookie、Firestore、チャット履歴へ入れない
- ログインの成否にかかわらず、フロントの入力欄から消す

実装は`backend/internal/wiki/auth.go`と`backend/internal/server/server.go`にあります。

ここを変更するときは、上の5つが崩れていないか必ず確認してください。

## セッションCookie

一度ログインしたら、毎回パスワードを入れ直さなくて済むようにしています。

そのために発行するのがセッションCookieです。中に入れているのは利用者名と有効期限だけで、
パスワードは入っていません。改ざんされないよう署名を付けています。

```
- 名前: `wasa_session`
- 内容
  - Base64URL化した利用者名
  - 有効期限
  - `SESSION_SECRET`を使ったHMAC-SHA256署名
- 有効期間: 30日
- 属性
  - `HttpOnly`
  - `Secure`
  - `SameSite=None`
  - `Partitioned`
  - `Path=/`
  ```

`SameSite=None`になっているのは、フロントエンド（Cloudflare Pages）と
バックエンド（Cloud Run）が別のドメインにあるためです。この設定にはHTTPSが必須になります。

**ログアウトしたとき**

- Cookieを失効させます
- 画面上の履歴を消します
- ただし、Firestoreに同期済みの履歴は削除しません（再ログインで復元されます）

**`SESSION_SECRET`の注意**

これは地味に重要なので強調しておきます。

- 本番では、32文字以上の固定値を必須にします
- 変更すると、全員がログアウトします
- さらに、Firestoreの利用者キーも変わるため、**既存の利用回数と履歴を参照できなくなります**

つまり、気軽に変えてよい値ではありません。

## 認証が必要なAPI

どのAPIにログインが要るかの一覧です。

**認証不要**

- `POST /api/login`
- `POST /api/logout`
- `GET /api/session`
- `GET /health`

**認証必須**

- `POST /api/ask`
- `GET /api/chats`
- `PUT /api/chats/{id}`
- `DELETE /api/chats/{id}`
- `POST /api/feedback`
- `GET /api/feedback`（`ADMIN_USERS`だけ）
- `GET /api/assistants`
- `POST /api/assistants`
- `PUT /api/assistants/{id}`
- `DELETE /api/assistants/{id}`

## CORS・CSRF・セキュリティヘッダー

フロントとバックが別ドメインにあるため、ブラウザ側の制限をきちんと設定する必要があります。

ここで注意が要るのは、**CORSヘッダーを返すだけではCSRF対策にならない**という点です。
Cookieが`SameSite=None`なので、悪意のあるサイトからでもCookie付きのPOSTが飛んできます。
そのため、許可していないOrigin自体を拒否しています。

- Cloud Runでは`ALLOW_ORIGIN`を必須にします（未設定なら起動しません）
- 複数の許可元はカンマ区切りにします
- 許可外Originからの状態変更リクエストは、403で拒否します
- 許可元にだけ次を返します
  - `Access-Control-Allow-Origin`
  - `Access-Control-Allow-Credentials: true`
- ローカル開発時だけ、localhost系ホストを同一扱いにします

セキュリティヘッダーは次のとおりです。

- `X-Frame-Options: DENY`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: no-referrer`
- CSPで、外部スクリプト、`object`、フレーム埋め込み、外部画像を拒否します

## Firestore保存構造

利用回数や履歴は、Google CloudのFirestoreへ保存しています。

ここで気をつけているのは、**誰のデータかが保存先から直接読み取れないようにする**ことです。
利用者名をそのままドキュメントIDにすると、保存先の一覧を見ただけで
「誰がいつ何回使ったか」が分かってしまいます。

**利用者キー**

- 利用者名を平文のドキュメントIDにしません
- 固定の`SESSION_SECRET`で`state|利用者名`をHMAC-SHA256化したものを使います

**利用回数**

- `users/{利用者HMAC}/usage/{日本時間の日付}`
- `used`と更新時刻を保存します

**チャット履歴**

- `users/{利用者HMAC}/chats/{chatId}`
- 最大30件
- 質問、回答、出典、回答モード、回答時のアシスタントID・名前、段階別所要時間を含みます

**共有アシスタント**

- `assistants/{assistantId}`
- 全員で共有するため、`users`配下へは置きません
- 作成者名は、責任の表示に必要なので平文で保存・表示します

**利用者フィードバック**

- `feedback/{feedbackId}`
- **保存期間は1年です。** 新しい報告が保存されるたびに、`submitted_at`が
  1年より古いものをサーバーが削除します（1回あたり最大100件）
  - 定期実行の仕組みを別に持たない方針なので、保存処理のついでに消しています。
    管理者の手作業に頼ると、プライバシーポリシーに書いた期間が守られません
  - 実装は`backend/internal/server/server.go`の`handleSaveFeedback`と、
    `state.Store`の`PurgeFeedback`です
- 報告者は、利用者名ではなくHMACキーで保存します
- 回答評価には、質問・回答・出典・段階別所要時間を含みます
- 画面全体の報告には、質問・回答を含めません
- 管理者APIは、報告者HMACキーを返しません
- Firestoreへの保存が先、管理者メールへの通知が後です。メール障害で保存を取り消しません
- メール本文へ、利用者名と報告者HMACキーを入れません

**ブラウザからの接続**

- Firestoreへ直接接続しません
- Wiki認証済みCookieを検証するGo APIだけを通します

## 利用回数

API費用が青天井にならないよう、利用者ごとに1日の質問数を制限しています。

これは単なる節約ではなく、**請求事故を防ぐための安全弁**です。

- 既定は、利用者1人あたり日本時間で1日30質問です
- `DAILY_LIMIT`で変更できます
- Firestoreのトランザクションで、質問の前に1回分を確保します
- 同時送信、別端末、Cookie削除、Cloud Run再起動でも、上限を共有します

Cookieではなくサーバー側で数えているので、ブラウザのデータを消してもリセットされません。

ただし、こちら側の都合で失敗したときにまで回数を減らすのは不公平なので、
次の場合は確保した分を返却します。

- Geminiの利用制限
- LLM通信障害
- 回答生成失敗

なお、アシスタントの取得失敗や不正な入力は、回数を確保する前に止めています。

## LLMへ送るデータ

非公開Wikiの内容を外部のAIへ送っている以上、何を送っていて何を送っていないかは
はっきりさせておく必要があります。

**送るもの**

- `facts.md`を含む目次
- 選択したWiki・公式サイトの本文
- 現在の質問
- 最大2往復の直近会話
- 選択した共有アシスタントの指示

**送らないもの**

- Wikiのパスワード
- Firestoreの全履歴
- 利用者名を含むセッションCookie
- `.env`

**Gemini無料枠について**

無料枠は、送信内容がGoogleの製品改善に使われる可能性があります。
非公開Wikiの本文を送る以上、これは技術判断だけで決めてよい話ではありません。

- 非公開Wiki本文を送るには、組織としての承認が必要です
- 2026-08-08のWASA会議で、代表・PMが承認しました
- 本番では、`GEMINI_PAID_TIER=true`または`GEMINI_FREE_TIER_APPROVED=true`が
  無ければ起動しません（承認を明示しないと動かない、という形にしてあります）

## リポジトリとデプロイ

コードは公開していますが、Wikiの中身は公開していません。

**コミットしないもの**

- `.env`
- `dump/`
- `data/`
- `eval/golden.json`

**公開フロントへ置かないもの**

- Wiki本文
- 索引
- APIキー
- セッション署名鍵

**Cloud Runでの受け渡し**

- `SESSION_SECRET`をSecret Managerから渡します
- `GEMINI_API_KEY`をSecret Managerから渡します
- `FIRESTORE_PROJECT_ID`と`ALLOW_ORIGIN`を必須にします

詳しくは[04-デプロイ手順.md](04-デプロイ手順.md)にあります。

## 利用者への説明

ここまでの内容のうち、利用者が知っておくべきことは
`web/public/support.html`（画面の「ヘルプとポリシー」）にまとめてあります。

- 取得する情報と目的、保存期間の一覧
- パスワードを保存しないこと
- 利用者名をHMAC化して保存していること
- 外部のAIサービスへ何を送り、何を送らないか
- 自分で削除できるもの（履歴・自作アシスタント）と、できないもの（匿名のフィードバック）

**この文書と`support.html`は、同じ事実を2か所に書いています。**
保存期間やマスキング範囲を変えるときは、必ず両方を直してください。
片方だけ直すと、利用者へ嘘の説明をすることになります。

## 確認

認証まわりを直したときは、次を実行してください。

```bash
cd backend
GOCACHE=/private/tmp/wasa-go-cache go test ./...

LIVE_WIKI_TEST=1 GOCACHE=/private/tmp/wasa-go-cache \
  go test ./internal/wiki -run '^TestLoginSuccess$'
```

最後に、この文書の内容を変えるときの注意です。

- 通常のテストは模擬Wikiを使うので、外部へは接続しません
- 実Wikiでテストするときの秘密値は、`.env`だけに置いてください
- **認証方式や個人情報のマスキング範囲を変えるときは、先に人間の判断を得てください。**
  技術的に正しいかどうかとは別に、サークルのデータをどう扱うかという判断が要る部分です
