# WASA Chat デプロイ手順

## 構成

- フロントエンド
  - Cloudflare Pages
  - `web/` をViteでビルドする
  - 利用者のブラウザからCloud Run APIを呼ぶ
- バックエンド
  - Google Cloud Run（`asia-northeast1`）
  - Artifact Registryに置いたDockerイメージを実行する
  - Wiki認証、検索、Gemini呼び出しを担当する
- 共有状態
  - Firestore（Native mode / `asia-northeast1`）
  - HMAC化した利用者キーごとに日次使用回数と最大30件のチャット履歴を保存する
  - 共有アシスタントと利用者フィードバックも保存する
- 非公開データ
  - `data/index.json` と `data/toc.md` はローカルからDockerイメージへ直接入れる
  - GitHub、Cloudflare Pages、公開レジストリへ置かない
  - `.env`、`dump/`、`eval/golden.json` はDockerイメージにも入れない

## デプロイ前の必須確認

- [ ] `git status` に `.env`、`dump/`、`data/`、`eval/golden.json` が出ていない
- [ ] `data/index.json` と `data/toc.md` を最新のWikiから手動で再生成した
- [ ] `cd backend && go test ./...` が成功する
- [ ] `cd web && npm ci && npm run build` が成功する
- [ ] Cloud Run利用のためGoogle Cloudの請求先を設定する
- [ ] Geminiの利用枠を確認する（無料枠への非公開Wiki送信は2026-08-08のWASA会議で代表・PMが承認済み）
- [ ] Google Cloud Billingの予算アラートを設定した
- [ ] `SESSION_SECRET` を32文字以上の乱数で作成した
- [ ] `ADMIN_USERS` に管理者のWiki利用者名を決めた（アシスタントの削除権限と初期アシスタントの作成者になる）
- [ ] Firestoreを`asia-northeast1`に作成し、削除保護を有効にした
- [ ] Cloudflare Pagesの本番URLが決まっている

## 1. Google Cloudを準備する

- 以降の例では、次の値を自分の環境に置き換える
  - `PROJECT_ID`: Google CloudのプロジェクトID
  - `REGION`: `asia-northeast1`
  - `REPOSITORY`: `wasa-chat`
  - `SERVICE`: `wasa-chat-api`
  - `FRONTEND_ORIGIN`: Cloudflare Pagesの本番URL（例: `https://wasa-chat.pages.dev`）
- Google Cloud CLIへログインし、プロジェクトを選ぶ

```bash
gcloud auth login
gcloud config set project PROJECT_ID
gcloud config set run/region asia-northeast1
```

- 必要なAPIを有効化する

```bash
gcloud services enable \
  run.googleapis.com \
  artifactregistry.googleapis.com \
  secretmanager.googleapis.com \
  firestore.googleapis.com \
  aiplatform.googleapis.com
```

- FirestoreをCloud Runと同じ東京リージョンに作成する

```bash
gcloud firestore databases create \
  --database='(default)' \
  --location=asia-northeast1 \
  --type=firestore-native \
  --delete-protection
```

- Cloud Runの実行サービスアカウントへ、Firestoreの読み書き権限`roles/datastore.user`を付与する
- ブラウザ用のFirebase SDKやFirestore Security Rulesからは接続せず、Cloud Runのサービスアカウントだけを使う

- Dockerイメージ用の非公開リポジトリを作る

```bash
gcloud artifacts repositories create wasa-chat \
  --repository-format=docker \
  --location=asia-northeast1 \
  --description="WASA Chat本番イメージ"

gcloud auth configure-docker asia-northeast1-docker.pkg.dev
```

## 2. シークレットを登録する

- セッション署名鍵を生成する

```bash
openssl rand -base64 48
```

- 出力を `wasa-session-secret` としてSecret Managerへ登録する
- Gemini APIキーを `wasa-gemini-api-key` として登録する
- シークレット値をコマンド履歴やリポジトリへ残さないため、Google Cloud Consoleからの登録を推奨する
- Wikiの利用者名とパスワードは登録しない
  - ログイン時に各利用者が入力し、バックエンドがWikiへ中継する
  - 本番サーバーへ固定のWikiパスワードを置く必要はない

- 回答モード別モデル
  - 既定は全段階で`gemini-3.5-flash-lite`を使う
  - 比較測定で改善を確認した場合だけ`GEMINI_FAST_MODEL`、`GEMINI_STANDARD_MODEL`、
    `GEMINI_DEEP_MODEL`をCloud Runの環境変数へ追加する
  - ブラウザからモデルIDは指定させない

## 3. Dockerイメージを作って送る

- Apple Silicon上でもCloud Runの実行形式に合わせて`linux/amd64`で作る
- タグは追跡できるようにGitコミットIDを使う

```bash
IMAGE=asia-northeast1-docker.pkg.dev/PROJECT_ID/wasa-chat/wasa-chat-api:$(git rev-parse --short HEAD)
docker buildx build --platform linux/amd64 --load -t "$IMAGE" .
docker push "$IMAGE"
```

- `data/index.json` と `data/toc.md` はこのイメージに含まれる
- Artifact Registryを公開設定にしない
- Wikiを更新した場合は、索引を再生成して新しいタグで作り直す

## 4. Cloud Runへデプロイする

```bash
gcloud run deploy wasa-chat-api \
  --image "$IMAGE" \
  --region asia-northeast1 \
  --allow-unauthenticated \
  --min-instances 0 \
  --max-instances 1 \
  --concurrency 20 \
  --cpu 1 \
  --memory 1Gi \
  --timeout 300 \
  --set-env-vars "^@^LLM_PROVIDER=gemini@GEMINI_FREE_TIER_APPROVED=true@DAILY_LIMIT=30@FIRESTORE_PROJECT_ID=PROJECT_ID@ALLOW_ORIGIN=FRONTEND_ORIGIN@ADMIN_USERS=42 Wasa Taro" \
  --set-secrets "SESSION_SECRET=wasa-session-secret:latest,GEMINI_API_KEY=wasa-gemini-api-key:latest"
```

⚠️ **`--set-env-vars` の先頭の `^@^` を消さないこと。** これは区切り文字をカンマから
`@` に変える指定である。`ADMIN_USERS` は「複数人ならカンマ区切り」かつ
「Wikiの利用者名に空白が入る」（例: `42 Wasa Taro`）ため、既定のカンマ区切りのままだと
利用者名が途中で分割され、**誰も管理者にならないまま静かに起動する**。

- `--allow-unauthenticated` はAPIそのものを公開到達可能にする設定
  - アプリ内ではWikiアカウントによるログインを引き続き必須にする
- `min-instances=0`
  - 未使用時のCloud Run費用を抑える
- `max-instances=1`
  - Geminiへの送信間隔と停止状態を現在はプロセス内で管理しているため、初期運用は1台に固定する
- `ALLOW_ORIGIN`
  - パスを含めず、Cloudflare PagesのOriginだけを指定する
  - プレビュー環境も認証付きAPIへ接続する場合はカンマ区切りで追加する
- `GEMINI_FREE_TIER_APPROVED=true`
  - 2026-08-08のWASA会議で代表・PMが非公開Wiki本文の無料枠への送信を許可したことを示す
  - 将来有料枠へ切り替えた場合は、確認後に`GEMINI_PAID_TIER=true`を使う

- デプロイ後にAPI URLを取得する

```bash
gcloud run services describe wasa-chat-api \
  --region asia-northeast1 \
  --format='value(status.url)'
```

- `https://...run.app/health` が200を返すことを確認する
  - Cloud Runでは末尾が`z`の一部パスがプラットフォーム側で処理されるため、`/healthz`は使わない

## 5. Cloudflare Pagesへデプロイする

- Cloudflare Dashboardで `Workers & Pages` → `Create` → `Pages` → `Connect to Git` を選ぶ
- GitHubのWASA Chatリポジトリを選ぶ
- ビルド設定
  - Production branch: `main`
  - Root directory: `web`
  - Build command: `npm run build`
  - Build output directory: `dist`
- 環境変数
  - `NODE_VERSION`: `24`
  - `VITE_API_ORIGIN`: 手順4で取得したCloud RunのURL
  - `VITE_WIKI_URL`: WASA WikiのURL
- 最初のPages URLが発行されたら、Cloud Runの `ALLOW_ORIGIN` をそのURLへ更新する

```bash
gcloud run services update wasa-chat-api \
  --region asia-northeast1 \
  --update-env-vars "ALLOW_ORIGIN=https://発行された名前.pages.dev"
```

- Cloudflare Pagesを再デプロイし、ブラウザで次を確認する
  - Wikiの利用者名とパスワードでログインできる
  - 「許可されていない送信元です」が出ない
  - 質問、進捗表示、Markdown、TeX、参照資料が表示される
  - 再ログイン後も当日の残り回数が維持される
  - 別端末でログインしても当日の残り回数とチャット履歴が一致する
  - ログアウト後は画面から履歴が消え、再ログインするとFirestoreから復元される

## 6. 更新とロールバック

- 更新
  - `main`を最新にする
  - Wikiと公式サイトを必要に応じて再取得する
  - `build_index.py`と`build_toc.py`を実行する
  - テスト後、新しいコミットIDのDockerタグをpushする
  - Cloud Runを新しいイメージへ更新する
- ロールバック
  - Cloud Runのリビジョン一覧から直前の正常なリビジョンへトラフィックを戻す
  - Artifact Registryの古い正常イメージをすぐ削除しない
- シークレット更新
  - Gemini APIキーはSecret Managerで新バージョンを作る
  - `SESSION_SECRET`を変えると全員がログアウトし、HMAC利用者キーも変わるため既存の利用回数と履歴を参照できなくなる

## 7. 運用上の注意

- Geminiの429は「遅くなるだけ」ではない
  - 短時間上限では、指定時間後の再試行で回復する場合がある
  - 日次上限では、リセットまで生成できない
  - WASA Chatは待機理由と再開見込みを画面へ表示する
- 利用者単位の30回制限
  - HMAC化した利用者キー、日本時間の日付、使用回数をFirestoreへ保持する
  - Firestoreトランザクションで確保するため、Cloud Run再起動、Cookie削除、別端末でもリセットしない
- チャット履歴
  - 質問・回答・出典を含むため、Firestoreの権限をCloud Run実行サービスアカウント以外へ広げない
  - 利用者ごとに新しい30件だけを保持し、個別削除はFirestoreにも反映する
- フィードバック
  - 回答評価には質問・回答・出典が含まれるため、Firestoreの権限を広げない
  - 最近の報告を取得できるのは`ADMIN_USERS`だけにする
  - 報告者の利用者名は保存せず、HMACキーも管理者APIへ返さない
- Geminiのプロジェクト全体制限
  - 現在は1インスタンス内で送信間隔を制御する
  - `max-instances`を2以上にする前に、共有レート制限用の外部ストアを設計する
