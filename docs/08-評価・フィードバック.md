# WASA Chat 評価・フィードバック

自動評価、人手評価、実利用者フィードバックの役割と、現在の改善候補をまとめる。
個々の測定結果と再現コマンドは[02-測定結果.md](02-測定結果.md)を正本とする。

## 現在の評価制度

- 検索評価
  - ゴールデンデータは33問
  - 検索採点対象は31問
  - 正解ページだけでなく、根拠チャンクを問ごとに指定する
  - 主指標はEvidence Recall@k
  - Page Recallだけを見ると実力を17ポイント過大評価したため、主指標にしない
  - 直近の全体値はEvidence Recall@5が17/31（54.8%）、Page Recall@5が21/31（67.7%）
- 生成評価
  - 出典形式などの決定的なルール検査
  - Faithfulness、Answer Relevancy、CompletenessのLLM-as-a-Judge
  - 正解チャンクを直接渡すOracle-context評価で、検索と生成の失敗を分ける
  - Geminiで測定できた時点のFaithfulnessは26/31（83.9%）
  - 判定器と人手評価の一致度は未測定なので、Faithfulnessを確定値として扱わない
- 人手評価
  - 方針は月1回20問
  - LLM判定とのCohen's κとfalse-accept率を測る
  - 現時点では未実施
- モード・アシスタント比較
  - 比較スクリプトは実装済み
  - Gemini APIのプリペイド残高不足により、完了0件
  - 「じっくり」やアシスタントが何ポイント高精度かはまだ断定できない
- 実利用者評価
  - この機能追加前は収集手段が無かった
  - 自動評価が見落とす「役に立ったか」「使いにくいか」を今回から収集する

## 利用者フィードバック

- 回答ごとの評価
  - 完了した回答に👍と👎を表示する
  - 1タップした時点で保存する
  - 理由と文章は任意にする
  - 同じ回答への再送は新規追加ではなく上書きする
  - 評価済み状態をチャット履歴にも残す
- 良い評価の任意理由
  - 知りたいことが分かった
  - 説明が分かりやすい
  - 出典が役立った
- 改善評価の任意理由
  - 内容が違う
  - 必要な情報がない
  - 説明が分かりにくい
  - 出典が違う
  - 情報が古い
  - 回答が遅い
- 画面全体の報告
  - 右上の「改善を送る」から開く
  - 表示・動作がおかしい
  - 使いにくい
  - 機能の提案
  - 回答・資料について
  - その他
  - 分類を1つ押した時点で保存し、補足文は任意にする
- 管理者
  - `ADMIN_USERS`だけが最近100件を取得できる
  - 画面上では直近12件の詳細を確認できる
  - 良い／改善／画面全体の件数を確認できる
  - 報告者の利用者名・HMACキーはAPIレスポンスへ出さない

## 保存とプライバシー

- 保存先
  - Firestoreの`feedback/{feedbackId}`
  - 回答評価のIDは利用者HMACキーとチャット・回答位置から決定的に作る
  - 同じ回答の理由や補足を後から更新できる
- 回答評価で保存するもの
  - 👍／👎
  - 任意理由と任意補足
  - 質問、回答、出典
  - アシスタントと回答モード
  - チャットIDと回答位置
- 画面全体の報告で保存するもの
  - 分類、任意補足、現在の画面
  - 質問・回答は保存しない
- 利用者
  - Wiki利用者名は保存しない
  - サーバー内部ではHMAC化した利用者キーを重複防止にだけ使う
  - 管理者画面へ利用者キーを返さない

## 改善への使い方

- 👍率だけを「精度」と呼ばない
  - 有用性の主観評価であり、事実の正しさとは別である
- 👎を理由別に分ける
  - `内容が違う`、`出典が違う`: Faithfulnessと根拠を人手確認する
  - `必要な情報がない`: ページ・チャンク選択を再現する
  - `説明が分かりにくい`: 回答形式と網羅性を確認する
  - `情報が古い`: 本文年代の抽出と資料自体の更新を分ける
  - `回答が遅い`: モードと段階別の待ち時間を確認する
- 実際の誤答だけを回帰データにする
  - Wiki・公式サイトの実データへevidenceを照合する
  - 検索失敗ならゴールデンデータと検索規則へ反映する
  - 資料の読み違いなら生成評価へ反映する
  - 資料を素直に読むと誤る場合だけ`facts.md`を検討する
- 自動でプロンプトへ追加しない
  - 利用者の主観、誤操作、資料の誤りが混ざるため、人手確認を必須にする

## 現在の改善候補

- 優先度A: 精度の未検証部分
  - API残高復旧後、TR797と追質問をエンドツーエンドで再測定する
  - 汎用と区分アシスタントを同じ質問・同じモデルで比較する
  - fast / standard / deepを複数回測り、精度、待ち時間、費用を比較する
  - LLM Judgeと人手20問のκ、false-accept率を測る
- 優先度A: 実利用フィードバックの運用
  - まず一定期間集め、理由別の件数と代表例を確認する
  - 👎件数ではなく、質問数に対する回答評価率と👎率を分母付きで見る
  - 報告から修正した問題をゴールデンデータへ追加し、再発を防ぐ
- 優先度B: 観測性
  - ページ選択、節選択、回答生成ごとの所要時間を保存する
  - `回答が遅い`を主観だけでなく実測値と結び付ける
  - どの回答モード・アシスタントで👎が多いかを比較する
- 優先度B: 検索
  - 現在のEvidence Recall@5は54.8%で、改善余地が大きい
  - 数字を含まない略語は、実際の誤答が出たものから対応する
  - `partial`と`global`の失敗を優先して分析する
- 優先度B: 画像
  - Wiki添付画像67枚のうち、回路図・設計図が回答に必要かサンプル確認する
  - 必要性が確認できた場合だけ画像処理を追加する
- 優先度C: フロントエンド
  - Markdown / KaTeXの遅延読込は実装済み。初回JavaScriptは243.23kB（gzip 76.20kB）へ減少した（M15）
  - 追加のコード分割は、初回チャンクが再び500kBへ近づいた場合に対象を測定して行う
  - フィードバック一覧の期間・理由フィルターとエクスポートは、100件で探しにくくなってから足す
  - キーボード操作とスクリーンリーダーでフィードバック動線を確認する
