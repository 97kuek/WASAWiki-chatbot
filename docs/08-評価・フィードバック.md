# WASA Chat 評価・フィードバック

ここでは、LLMによる出力の精度や品質をどのように測っているのか・どのようにフィードバックしているのかをまとめたドキュメントです。

チャットボットは、それらしい文章さえ返せば動いているように見えてしまいます。
**「動いている」と「正しく答えている」は別物**なので、数字で測れる形にしておかないと、
静かに間違え続けるアプリになります。そのための仕組みが、この文書の内容です。

なお、個々の測定結果と再現コマンドは[02-測定結果.md](02-測定結果.md)を正本とします。

## 現在の評価制度

現在の評価制度は以下の通りになっています。

大きく分けると、**資料を正しく探せているか（検索）**と、
**探した資料から正しく答えているか（生成）**の2つを別々に測っています。

これを混ぜると、精度が悪かったときに検索が悪いのか生成が悪いのか切り分けられず、
どこを直せばいいのか分からなくなります。

### 検索評価

- ゴールデンデータと呼ばれる、検索精度を評価する正解つきの問題集は全部で33問あり、そのうち検索の採点対象は31問あります
- 正解ページだけでなく、**根拠となるチャンクまで**問ごとに指定しています
- 主指標はEvidence Recall@kです
- Page Recall（ページ単位）だけを見ると実力を17ポイント過大評価したため、主指標にしません
- 直近の全体値は、Evidence Recall@5が17/31（54.8%）、Page Recall@5が21/31（67.7%）です
- LLMを使わない型番・実在タイトル候補は、正解ページを20/31（64.5%）で保証します
- ただしこの20/31は最終的なPage Recallではありません。
  **モデルの選択が失敗しても落ちない下限**として、別に記録しています

**生成評価**

- 出典形式などの、決定的なルール検査
- Faithfulness、Answer Relevancy、CompletenessのLLM-as-a-Judge
- 正解チャンクを直接渡すOracle-context評価で、検索と生成の失敗を分けます
- Geminiで測定できた時点のFaithfulnessは26/31（83.9%）です
- ただし、判定器と人手評価の一致度が未測定なので、Faithfulnessを確定値として扱いません

**人手評価**

- 方針は月1回20問です
- LLM判定とのCohen's κ（一致度）とfalse-accept率を測ります
- 現時点では未実施です

**モード・アシスタント比較**

- 比較スクリプトは実装済みです
- ただしGemini APIのプリペイド残高不足により、完了0件です
- したがって「じっくり」やアシスタントが何ポイント高精度かは、まだ断定できません

**TR797・追質問**

- q32・q33だけを指定する対象限定評価と、HTTPから回答プロンプトまでの決定的E2Eを実装済みです
- 決定的E2Eは2/2件通過しましたが、Gemini生成は残高不足で0/2件のため、回答品質は未測定です

**実利用者評価**

- この機能を追加する前は、収集手段がありませんでした
- 自動評価が見落とす「役に立ったか」「使いにくいか」を、今回から収集します

## 利用者フィードバック

自動評価はゴールデンデータ33問しか見ていません。

実際の利用者がどんな質問をして、何に困ったかは、そこには現れません。
そこで画面から直接受け取れるようにしました。

設計の要点は、**送信の負担をできるだけ下げること**です。文章を必須にすると誰も送りません。

**回答ごとの評価**

- 完了した回答に👍と👎を表示します
- 1タップした時点で保存します
- 理由と文章は任意です
- 同じ回答への再送は、新規追加ではなく上書きします（件数を水増ししないためです）
- 評価済み状態は、チャット履歴にも残します

良い評価につけられる任意の理由は次の3つです。

- 知りたいことが分かった
- 説明が分かりやすい
- 出典が役立った

改善評価につけられる任意の理由は次の6つです。あとで原因を切り分けられるよう、
「何が違ったのか」で分けてあります。

- 内容が違う
- 必要な情報がない
- 説明が分かりにくい
- 出典が違う
- 情報が古い
- 回答が遅い

**画面全体の報告**

- 右上の「改善を送る」から開きます
- 「匿名で管理者にフィードバックを送れます」とだけ説明します
- 分類は、表示・動作がおかしい／使いにくい／機能の提案／回答・資料について／その他 の5つです
- 分類を1つ選び、「送信する」を押した時点で保存します
- 分類を押しただけでは送信しません。補足文は任意です
- スマホでは分類を縦に並べ、ポップアップを画面内でスクロールできるようにします

回答評価は1タップで送るのに、こちらは送信ボタンを挟んでいるのは意図的です。
分類を押した瞬間に送ってしまうと、内容を見直す前に保存されて取り消せなくなるためです。

**管理者から見える範囲**

- `ADMIN_USERS`だけが、最近100件を取得できます
- 画面上では、直近12件の詳細を確認できます
- 良い／改善／画面全体の件数を確認できます
- 報告者の利用者名・HMACキーは、APIレスポンスへ出しません
- `FEEDBACK_EMAIL_TO`を設定すると、保存後に管理者へメールでも通知します
- メール通知に失敗してもFirestoreの保存は取り消さず、
  画面に「保存済み・通知失敗」と表示します

## 保存とプライバシー

フィードバックには質問文や回答が含まれます。非公開Wikiの内容が入る可能性があるので、
保存する範囲は最小限にしています。

**保存先**

- Firestoreの`feedback/{feedbackId}`
- 回答評価のIDは、利用者HMACキーとチャット・回答位置から決定的に作ります
- そのため、同じ回答の理由や補足を後から更新できます

**保存期間は1年です**（2026-08-09に人間が判断）。

改善の振り返りに使えるだけの長さを取りつつ、サークル内のデータを無期限に
持ち続けないための期間です。新しい報告を保存するたびに、1年より古いものを
サーバーが自動で削除します。管理者の手作業には頼っていません。

**メール通知**

- SMTP（メール送信サービスへメールを渡す方法）を使います
- 宛先、送信元、認証情報は環境変数に置き、コードへメールアドレスを書きません
- 通知本文へ、Wiki利用者名とHMACキーを入れません
- 回答は先頭2,000文字まで通知し、全文の正本はFirestoreとします

**回答評価で保存するもの**

- 👍／👎
- 任意理由と任意補足
- 質問、回答、出典
- アシスタントと回答モード
- ページ選択、節選択、回答生成、合計の所要時間
- チャットIDと回答位置

**画面全体の報告で保存するもの**

- 分類、任意補足、現在の画面
- 質問・回答は保存しません

**利用者について**

- Wiki利用者名は保存しません
- サーバー内部では、HMAC化した利用者キーを重複防止にだけ使います
- 管理者画面へ、利用者キーを返しません

## 改善への使い方

集めたフィードバックを、どう改善へ戻すかです。

ここで一番大事なのは、**👍率を「精度」と呼ばないこと**です。
👍率は「役に立ったと感じたか」という主観であって、事実として正しかったかとは別の話です。
両方見る必要はありますが、混ぜてはいけません。

**👎は理由別に分けて調べます**

理由ごとに、確認すべき場所が違います。

| 理由 | 確認すること |
|---|---|
| 内容が違う / 出典が違う | Faithfulnessと根拠を人手確認する |
| 必要な情報がない | ページ・チャンク選択を再現する |
| 説明が分かりにくい | 回答形式と網羅性を確認する |
| 情報が古い | 本文年代の抽出と、資料自体の更新を分ける |
| 回答が遅い | モードと段階別の待ち時間を確認する |

**実際の誤答だけを回帰データにします**

- Wiki・公式サイトの実データへevidenceを照合します
- 検索の失敗なら、ゴールデンデータと検索規則へ反映します
- 資料の読み違いなら、生成評価へ反映します
- 資料を素直に読むと誤る場合だけ、`facts.md`を検討します

**自動でプロンプトへ追加してはいけません**

利用者の主観、誤操作、資料そのものの誤りが混ざっているため、人手確認を必須にします。
報告をそのまま規則にすると、プロンプトが際限なく伸びていきます。

## 現在の改善候補

いま分かっている「やるべきこと」を、優先度順に並べています。

作業リストとしての最新版は[TODO.md](../TODO.md)にあります。こちらは
評価という観点から見た整理だと考えてください。

**優先度A: 精度の未検証部分**

- API残高の復旧後、対象限定コマンドでTR797と追質問の実モデル回答を再測定する
- 汎用と区分アシスタントを、同じ質問・同じモデルで比較する
- fast / standard / deepを複数回測り、精度、待ち時間、費用を比較する
- LLM Judgeと人手20問のκ、false-accept率を測る

**優先度A: 実利用フィードバックの運用**

- まず一定期間集め、理由別の件数と代表例を確認する
- 👎の件数ではなく、質問数に対する回答評価率と👎率を、分母付きで見る
- 報告から修正した問題をゴールデンデータへ追加し、再発を防ぐ

**優先度B: 観測性**

- ページ選択、節選択、回答生成、合計の所要時間の保存は実装済み
- `回答が遅い`の報告では、管理者画面に同じ回答の段階別所要時間を表示する
- 実利用データが集まってから、段階ごとの分布と外れ値を測る
- どの回答モード・アシスタントで👎が多いかを比較する

**優先度B: 検索**

- 現在のEvidence Recall@5は54.8%で、改善の余地が大きい
- 数字を含まない略語は、実際の誤答が出たものから対応する
- `partial`と`global`の失敗を優先して分析する

**優先度B: 画像**

- Wiki添付画像67枚の必要性は測定済み（M21）。図が唯一の情報源なのは15箇所
- ただしゴールデンデータの正解チャンクに図は0件のため、画像処理はまだ追加しない
- 追加する場合の対象は、数式画像10枚と`EE-SX460-P1 ピン配置.png`の計11枚に限る

**優先度C: フロントエンド**

- Markdown / KaTeXの遅延読込は実装済み。初回JavaScriptは243.23kBへ減少した（M15）
- 追加のコード分割は、初回チャンクが再び500kBへ近づいた場合に対象を測定して行う
- フィードバック一覧の期間・理由フィルターとエクスポートは、100件で探しにくくなってから足す
- キーボード操作の不足はM22で修正済み。スクリーンリーダーの実機確認は未実施
