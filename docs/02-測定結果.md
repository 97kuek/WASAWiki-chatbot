## M1. 検索ベースライン（BM25 / 文字bigram）

- 日付: 2026-08-06
- 対象: チャンク348件、ゴールデンデータ31問（うち検索採点対象29問）
- 実行: `python eval/retrieval_eval.py`
- 検索器: 文字bigramのBM25（形態素解析器なし、外部依存なし）

| k | Evidence Recall | All-Evidence Recall | Page Recall |
|---:|---:|---:|---:|
| 1 | 24.1% | 20.7% | 31.0% |
| 3 | 41.4% | 37.9% | 69.0% |
| 5 | **55.2%** | 41.4% | **72.4%** |
| 10 | 69.0% | 55.2% | 82.8% |

MRR: **0.390** ／ 無情報ベースライン（インデックス順）: Recall@5 = 6.9%, MRR = 0.080

### 種別ごとの Hit@5

| 種別 | 結果 |
|---|---|
| procedure | 5/7 |
| fact | 7/11 |
| partial | 3/5 |
| global | 1/2 |
| comparison | **0/2** |
| false_premise | **0/1** |
| unanswerable | **0/1** |

### 読み取れたこと

**1. ページ単位のRecallは実力を17ポイント過大評価する。**

`Page Recall@5 = 72.4%` に対し `Evidence Recall@5 = 55.2%`。設計方針 §5-3 で
「36,261字ある『駆動・フレーム班』がヒットしても正解の節が取れているとは限らない」
と書いた懸念が、そのまま17ポイントの差として出た。**ページ単位で測っていたら
実力を見誤っていた。** ゴールデンデータをチャンク単位で作った判断は正しかった。

**2. 語彙検索が原理的に弱い領域が、そのまま0%として出た。**

comparison（2問）、false_premise（1問）、unanswerable（1問）がすべて Hit@5 = 0。

- q18「早稲田大学の滑空機はどうやって作るのですか？」→ 正解の順位 **98位**。
  前提が誤っている質問は、質問文の語彙が正解チャンクと重ならないため原理的に引けない
- q10「41stと40thの空力設計の違い」→ **24位**。比較質問は2つの対象を1クエリで
  表すため、どちらのチャンクとも中途半端にしかマッチしない
- q29「40代はどういう活動をしたのか」→ **43位**。全域型も同様

これらは検索器のチューニングでは埋まらない。**クエリ書き換え（比較質問を2本に割る）
や、メタデータフィルタ（代=40で絞る）といった別の層が要る**という根拠になった。

**3. k=5 では足りず、k=10 で69%。**

Recall@10 が Recall@5 を14ポイント上回る。候補を広く取ってリランキングする構成
（設計方針 §6-4）に合理性がある。

### この数字の位置づけ

これは**検索層のみ**の性能であり、Phase 1 で作る「目次方式（L1）」とは
比較対象が違う。目次方式はClaudeが目次を見てページを選ぶため、
上表の語彙一致とは別の経路で正解に到達しうる。**両者を同じ設問で測って
初めて、検索層（Phase 2）が必要かどうかが判断できる。**

次の測定 M2 は「目次方式のみ、検索層なし」。Anthropic APIキーが必要。

## M2a. 目次方式によるページ選択（検索層なし）

- 日付: 2026-08-06
- 対象: 目次14,743字（10,288トークン）、ゴールデンデータ31問（ページ採点対象29問）
- 実行: `python eval/toc_eval.py`
- モデル: **qwen3:30b-a3b（ローカル / Ollama）**。非公開Wikiのデータを外部に出さないため

| 指標 | 結果 |
|---|---|
| **Page Recall@3** | **93.1%** (27/29) |
| All-Pages Recall@3 | 72.4% (21/29) |
| 1位が正解 | 82.8% (24/29) |
| 回答可否の判定 | 74.2% (23/31) |
| 平均所要 | 3.9秒/問（合計122秒） |

### BM25ベースライン（M1）との比較 ※ページ単位で粒度を揃えてある

| 手法 | Page Recall |
|---|---|
| BM25 @3 | 69.0% |
| BM25 @5 | 72.4% |
| **目次方式 @3** | **93.1%** |

**目次方式は BM25 を24ポイント上回った。** BM25の@5（72.4%）すら21ポイント上回っている。

### 種別ごとの Hit（BM25との対比）

| 種別 | BM25 Hit@5 | 目次方式 Hit@3 |
|---|---|---|
| fact | 7/11 | **11/11** |
| procedure | 5/7 | **7/7** |
| comparison | **0/2** | **2/2** |
| global | 1/2 | **2/2** |
| partial | 3/5 | 4/5 |
| unanswerable | 0/1 | 1/1 |
| false_premise | 0/1 | **0/1** |

### 読み取れたこと

**1. 語彙検索が原理的に弱かった領域を、目次方式が埋めた。**

M1 で「comparison 0/2、global 1/2 は検索器のチューニングでは埋まらない」と書いた。
目次方式ではそれぞれ **2/2、2/2**。q10（41st と 40th の比較）はBM25で24位だったが、
目次方式は両方のページを正しく選んでいる。**LLMが目次全体を見て判断する経路は、
語彙一致とは別物として機能している。**

**2. Phase 2（検索層）の優先度は下がった。**

93.1%という数字は、検索層を足す前の Phase 1 単体のもの。**まず検索層なしで進め、
不足が具体化してから足す**という §2 の方針が、数字で裏付けられた。

**3. ハルシネーション対策が必須。存在しないページ名を8件返した。**

| 質問 | 返した架空のタイトル | 正体 |
|---|---|---|
| q31 | 「空力」「構造」「翼」 | **班名**をページ名として返した |
| q20 | 「鳥コンまでの流れ」「鳥コンスケジュール」 | **節名**をページ名として返した |
| q23 | 「構造設計 41st」 | 命名規則から**推測して生成**した（実ページは未作成） |
| q18 | 「WASA Wiki 目次」「質問: 早稲田大学の…」 | プロンプトの一部をそのまま返した |

→ **返ってきたタイトルは必ず目次と照合し、存在しないものは落とす。** 実装必須。

**4. 渡す文脈量が大きすぎる。ページ→チャンクの2段目が要る。**

選択した3ページの合計文字数は中央値9,770字だが、**最大48,100字**。
36,261字ある「駆動・フレーム班」を丸ごと渡すと文脈を圧迫する。
ページを選んだ後、そのページ内でチャンクを絞る2段目が必要。

**5. false_premise は両手法とも 0/1。**

q18「早稲田大学の滑空機はどうやって作るのですか？」は、BM25では98位、
目次方式ではプロンプトの一部をタイトルとして返して破綻した。
**前提が誤った質問は、検索でも目次選択でも拾えない。** 回答生成側で
「そもそもWASAは滑空機部門ではない」と気づかせる必要がある。

**6. リード文が空のページが5件ある。**

`メインページ / 役職決め / 合宿 / 駆動設計 / 電装39代設計コンセプト・反省`。
リード文が空だと目次の情報量が落ちる。q15（フライトシミュレーター）を外した一因と見られる
（メインページの節一覧には「フライトシミュレーター」が入っているが、リード文が空で、
語彙的に「フライトシミュレーターの開発もしている」と書かれた人物ページに負けた）。

### この数字の限界

**ローカルモデル（qwen3:30b-a3b）での測定である。** Claude で測り直せば数字は変わる。
ただし本測定の目的は**アーキテクチャの妥当性判断**であり、その点では十分に結論が出た。
回答品質（Faithfulness等）の測定 M2b は、本番モデルで別途行う必要がある。

## M2b. エンドツーエンドの回答品質

- 日付: 2026-08-07
- 対象: ゴールデンデータ31問
- 実行: `python eval/answer_eval.py`
- モデル: qwen3:30b-a3b（ローカル）。LLM呼び出し100回 / 合計1,753秒

### 結論を先に: **回答品質は測れなかった。アーキテクチャの検証はできた。**

ローカルモデルが「思考を書かない」「日本語で答える」という指示に安定して従わず、
回答本文に思考過程が混入した。`think:false`（API）、`/no_think`（qwen3のソフトスイッチ）、
プロンプトでの明示の3つを試したがいずれも効かなかった。したがって
**出典明示率とFaithfulnessの数字は、モデルの癖に汚染されており指標にならない。**

### アーキテクチャとして検証できたこと

| 項目 | 結果 | 判定 |
|---|---|---|
| ページ選択の的中 | 27/29 | ✅ M2aと同水準を再現 |
| 文脈量 | 中央値6,998字 / **最大12,645字** | ✅ M2aの48,100字から圧縮できた |
| 架空ページ名の除去 | **12件を捕捉** | ✅ ガードが機能 |
| 回答不能な問いで「記載なし」 | 6/8 | ✅ 機能している |

**2段絞り込みの効果が数字で出た。** M2a では選択3ページの合計が最大48,100字だったが、
パンくずだけを見せて節を選ばせる段を挟んだ結果、最大12,645字に収まった。

**ガードが捕捉した架空ページ名の内訳が示唆的である。**

| 種類 | 例 |
|---|---|
| 節名をページ名として返した | `作業場ルール` `パワメとは` `各種申請の流れについて` `鳥コン資料` |
| 推測で生成した | `42代駆動メモ` `HPA交流会関する引き継ぎ資料` |
| 班名 | `構造` `翼` |
| 空文字列 | `""` ×3（q15） |

ガードが無ければ、存在しないページを根拠として回答していた。**M2aで見つけた
課題への対処が、実際に効いていることが確認できた。**

### 測れなかったこと、およびその原因

**1. 出典明示 17/31 (54.8%)** — プロンプトで「出典: ページ名（最終更新: YYYY-MM）の形で
必ず挙げる」と指示しているが従わない。長い資料の後ろに指示を置くと効きにくい。

→ **アプリ側で構造的に解決する。** 回答本文にLLMが出典を書くことに頼らず、
SSEの `pages` イベントで送っている出典をUIが別枠で表示する（実装済み）。
**LLMの指示追従に依存しない設計に寄せる**という判断。

**2. Faithfulness 61.3%** — 判定器が機能していない。判定理由の欄に
「資料に書かれていない事実を述べていたら faithful = false」という
**判定基準の文をそのままオウム返し**していた。

→ スキーマの順序を変え、`unsupported_claim`（裏付けの無い記述の引用）を
先に書かせてから `faithful` を決める形に修正した。判定を先に置くと、
根拠を考える前に決めてしまう。

**3. 答えられる問いで誤って「記載がない」5件** — うち q07 は実際には正しく
作業場ルールを列挙しており、**検出用の正規表現の誤検知**だった。
残りは思考文の混入によるもの。

### 判断を変えた点

- **回答品質の測定は本番モデル（Claude）が要る。** ローカルモデルでの代替は
  アーキテクチャ検証までが限界。docs/01 §9 の M2b は「APIキー入手後に再実行」とする
- **出典の提示はLLMに依存しない。** UIが構造的に出す（実装済み）
- **判定器の検証は必須。** 「暫定値として扱う」では不十分で、
  実際に機能しているかを最初に確かめる必要がある

## 測定の型

新しい測定を足すときは以下を必ず書く。

- 日付 / 対象データの規模 / 再現コマンド
- 数字（表）
- **読み取れたこと**（数字から何を判断したか）
- **判断を変えた点**（設計方針のどこを書き換えたか）
