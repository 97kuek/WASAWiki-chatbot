## M1. 検索ベースライン（BM25 / 文字bigram）

- 日付: 2026-08-06
- 対象: チャンク348件、ゴールデンデータ31問（うち検索採点対象29問）
- 実行: `python eval/retrieval_eval.py`
- 検索器: 文字bigramのBM25（形態素解析器なし、外部依存なし）

| k | Evidence Recall | All-Evidence Recall | Page Recall |

MRR: **0.390** ／ 無情報ベースライン（インデックス順）: Recall@5 = 6.9%, MRR = 0.080

| 種別 | 結果 |
|---|---|
| procedure | 5/7 |

### 読み取れたこと

**1. ページ単位のRecallは実力を17ポイント過大評価する。**

`Page Recall@5 = 72.4%` に対し `Evidence Recall@5 = 55.2%`。設計方針 §5-3 で
「36,261字ある『駆動・フレーム班』がヒットしても正解の節が取れているとは限らない」
と書いた懸念が、そのまま17ポイントの差として出た。**ページ単位で測っていたら
実力を見誤っていた。** ゴールデンデータをチャンク単位で作った判断は正しかった。

**2. 語彙検索が原理的に弱い領域が、そのまま0%として出た。**

comparison（2問）、false_premise（1問）、unanswerable（1問）がすべて Hit@5 = 0。

- q18「早稲田大学の滑空機はどうやって作るのですか？」→ 正解の順位 **98位**。
  前提が誤っている質問は、質問文の語彙が正解チャンクと重ならないため原理的に引けない
- q10「41stと40thの空力設計の違い」→ **24位**。比較質問は2つの対象を1クエリで
  表すため、どちらのチャンクとも中途半端にしかマッチしない
- q29「40代はどういう活動をしたのか」→ **43位**。全域型も同様

これらは検索器のチューニングでは埋まらない。**クエリ書き換え（比較質問を2本に割る）
や、メタデータフィルタ（代=40で絞る）といった別の層が要る**という根拠になった。

**3. k=5 では足りず、k=10 で69%。**

Recall@10 が Recall@5 を14ポイント上回る。候補を広く取ってリランキングする構成
（設計方針 §6-4）に合理性がある。

### この数字の位置づけ

これは**検索層のみ**の性能であり、Phase 1 で作る「目次方式（L1）」とは
比較対象が違う。目次方式はClaudeが目次を見てページを選ぶため、
上表の語彙一致とは別の経路で正解に到達しうる。**両者を同じ設問で測って
初めて、検索層（Phase 2）が必要かどうかが判断できる。**

次の測定 M2 は「目次方式のみ、検索層なし」。Anthropic APIキーが必要。

**2. Phase 2（検索層）の優先度は下がった。**

93.1%という数字は、検索層を足す前の Phase 1 単体のもの。**まず検索層なしで進め、
不足が具体化してから足す**という §2 の方針が、数字で裏付けられた。

**3. ハルシネーション対策が必須。存在しないページ名を8件返した。**

**4. 渡す文脈量が大きすぎる。ページ→チャンクの2段目が要る。**

選択した3ページの合計文字数は中央値9,770字だが、**最大48,100字**。
36,261字ある「駆動・フレーム班」を丸ごと渡すと文脈を圧迫する。
ページを選んだ後、そのページ内でチャンクを絞る2段目が必要。

**5. false_premise は両手法とも 0/1。**

目次方式ではプロンプトの一部をタイトルとして返して破綻した。
**前提が誤った質問は、検索でも目次選択でも拾えない。** 回答生成側で

**6. リード文が空のページが5件ある。**

### この数字の限界

ただし本測定の目的は**アーキテクチャの妥当性判断**であり、その点では十分に結論が出た。

## M2b. エンドツーエンドの回答品質

- 日付: 2026-08-07
- 対象: ゴールデンデータ31問
- 実行: `python eval/answer_eval.py`
- モデル: qwen3:30b-a3b（ローカル）。LLM呼び出し100回 / 合計1,753秒

### 結論を先に: **回答品質は測れなかった。アーキテクチャの検証はできた。**

ローカルモデルが「思考を書かない」「日本語で答える」という指示に安定して従わず、
回答本文に思考過程が混入した。`think:false`（API）、`/no_think`（qwen3のソフトスイッチ）、
プロンプトでの明示の3つを試したがいずれも効かなかった。したがって
**出典明示率とFaithfulnessの数字は、モデルの癖に汚染されており指標にならない。**

### アーキテクチャとして検証できたこと

| 項目 | 結果 | 判定 |
|---|---|---|
| ページ選択の的中 | 27/29 | ✅ M2aと同水準を再現 |
| 文脈量 | 中央値6,998字 / **最大12,645字** | ✅ M2aの48,100字から圧縮できた |
| 架空ページ名の除去 | **12件を捕捉** | ✅ ガードが機能 |
| 回答不能な問いで「記載なし」 | 6/8 | ✅ 機能している |

**2段絞り込みの効果が数字で出た。** M2a では選択3ページの合計が最大48,100字だったが、
パンくずだけを見せて節を選ばせる段を挟んだ結果、最大12,645字に収まった。

**ガードが捕捉した架空ページ名の内訳が示唆的である。**

| 種類 | 例 |
|---|---|
| 節名をページ名として返した | `作業場ルール` `パワメとは` `各種申請の流れについて` `鳥コン資料` |
| 推測で生成した | `42代駆動メモ` `HPA交流会関する引き継ぎ資料` |
| 班名 | `構造` `翼` |
| 空文字列 | `""` ×3（q15） |

ガードが無ければ、存在しないページを根拠として回答していた。**M2aで見つけた
課題への対処が、実際に効いていることが確認できた。**

### 測れなかったこと、およびその原因

**1. 出典明示 17/31 (54.8%)** — プロンプトで「出典: ページ名（最終更新: YYYY-MM）の形で
必ず挙げる」と指示しているが従わない。長い資料の後ろに指示を置くと効きにくい。

→ **アプリ側で構造的に解決する。** 回答本文にLLMが出典を書くことに頼らず、
SSEの `pages` イベントで送っている出典をUIが別枠で表示する（実装済み）。
**LLMの指示追従に依存しない設計に寄せる**という判断。

**2. Faithfulness 61.3%** — 判定器が機能していない。判定理由の欄に
「資料に書かれていない事実を述べていたら faithful = false」という
**判定基準の文をそのままオウム返し**していた。

→ スキーマの順序を変え、`unsupported_claim`（裏付けの無い記述の引用）を
先に書かせてから `faithful` を決める形に修正した。判定を先に置くと、
根拠を考える前に決めてしまう。

**3. 答えられる問いで誤って「記載がない」5件** — うち q07 は実際には正しく
作業場ルールを列挙しており、**検出用の正規表現の誤検知**だった。
残りは思考文の混入によるもの。

### 判断を変えた点

- **回答品質の測定は本番モデル（Claude）が要る。** ローカルモデルでの代替は
  アーキテクチャ検証までが限界。docs/01 §9 の M2b は「APIキー入手後に再実行」とする
- **出典の提示はLLMに依存しない。** UIが構造的に出す（実装済み）
- **判定器の検証は必須。** 「暫定値として扱う」では不十分で、
  実際に機能しているかを最初に確かめる必要がある

## M2b-2. Gemini（無料枠）での再測定

- 日付: 2026-08-07
- モデル: **gemini-flash-lite-latest**（Google Gemini 無料枠）
- 実行: `LLM_PROVIDER=gemini python eval/answer_eval.py`

無料枠は送信内容が学習に使われうるが、そのリスクを承知のうえでの選択。
個人情報（メール・生年月日・電話番号）はマスク済み。

### ローカルモデルとの比較

| 指標 | qwen3:30b-a3b（ローカル） | gemini-flash-lite |
|---|---|---|
| ページ選択の的中 | **27/29 (93.1%)** | 24/29 (82.8%) |
| **出典の明示** | 17/31 (54.8%) | **31/31 (100%)** |
| **架空ページ名** | **12件** | **0件** |
| Faithfulness（判定器） | 61.3%（判定器が機能せず） | 80.6% |
| 所要 | 1,753秒 | **128秒** |

**M2bで「測れなかった」ものが測れるようになった。**

- **出典の明示が54.8% → 100%。** ローカルモデルが従わなかった
  「出典を必ず挙げる」という指示に、Geminiは全問で従った
- **架空ページ名が12件 → 0件。** 節名や班名をページ名として返す挙動が消えた
- **判定器が機能し始めた。** ローカルでは判定基準の文をオウム返ししていたが、
  Geminiは具体的な記述を引用してくる（例: q03で「2年以上経過している」という
  記述を、最終更新2026-04-28に対する誤りとして正しく指摘した）
- **13.7倍速い。** 128秒 vs 1,753秒

一方で**ページ選択はローカルの30Bモデルに10ポイント負けた**（93.1% → 82.8%）。
flash-lite は最小構成のモデルであり、指示追従は強いが判断力では劣る。
**指示追従と判断力は別の軸である**ことが数字で見えた。

### 自分の評価スクリプトの欠陥を2つ見つけた

**1. `partial` 型と `unanswerable` 型を同じ物差しで測っていた。**

回答本文に「記載がありません」が一度でも出れば「拒否した」と数えていた。
しかしプロンプトは「**何が書かれていて何が書かれていないかを分けて述べる**」と
指示している。つまり**指示どおりに答えた回答ほど誤検知される**構造だった。

種別ごとに基準を分けて再採点した結果:

| 種別 | 適切な回答の出し方 | 結果 |
|---|---|---|
| comparison | 2/2 | |
| false_premise | 1/1 | q18を正解。ローカルは0/1 |
| procedure | 6/7 | |
| fact | 8/11 | |
| partial | 2/5 | 欠落を認めつつ中身も出す、が難しい |
| unanswerable | 1/2 | |
| global | 1/3 | |
| **合計** | **21/31 (67.7%)** | |

**2. 「答えられるのに拒否」9件のうち、実際の拒否は6件だった。**
残り3件（q21, q27, q28）は、指示どおり「書かれていること／いないこと」を
分けて答えた**正しい回答**だった。

### 読み取れたこと

**指示追従は小さいモデルでも十分だが、判断力は別。**
ページ選択（どのページを読むべきかの判断）は30Bのローカルモデルが勝ち、
出力形式の遵守（出典・実在するページ名・日本語）はflash-liteが圧勝した。
**段によって求められる能力が違う**ので、本番では段ごとにモデルを変える設計が
合理的かもしれない（選択は賢いモデル、整形は安いモデル）。

**苦手な種別が明確になった。** `partial`（2/5）と `global`（1/3）。
「書かれていないことを、書かれていないと正しく言う」のが最も難しい。
これは docs/01 §5-3 で Faithfulness を最重要指標に置いた判断と整合する。

### 無料枠の制約（実測）

| モデル | 状況 |
|---|---|
| gemini-3.6-flash | **日次20リクエスト**。31問の測定に届かない |
| gemini-2.5-flash / 2.0-flash / 2.5-flash-lite | 上限到達済み or 無料枠対象外 |
| **gemini-flash-lite-latest** | 使用可。**思考トークン0**で出力予算を食わない |

Gemini 3.x系は思考トークンが `maxOutputTokens` を消費する。「1+1は？」でも
47トークン使い、予算50では本文がゼロ件で返ってきた。`thinkingBudget` は
3.6-flash では400エラーになるため `thinkingLevel: LOW` を指定する。

## M3. プロンプト改善（過剰な拒否の解消）

- 日付: 2026-08-07
- モデル: gemini-flash-lite-latest
- 比較対象: M2b-2（同じモデル・同じ設問）

### 何を直したか

M2b-2 の失敗10件を「検索の失敗」と「回答の作り方の失敗」に切り分けたところ、
**正しいページを選んでおきながら「Wikiには記載がありません」と答える**ケースが
最悪だった（q30・q23）。36,261字の「駆動・フレーム班」を渡されて記載なしと答えていた。

原因は回答プロンプトの偏りだった。**「書かれていないことは推測で補うな」しか
書いておらず、「読み取れることは整理して答えてよい」を書いていなかった。**
小さいモデルほど字義通りに受け取る。

| 変更 | 内容 |
|---|---|
| 回答プロンプトの再調整 | 「答えられることは答える」節を追加。要約・比較・時系列の整理は推測ではないと明示 |
| **回答段にも目次を渡す** | 全体を見渡す問い（q31「最も情報が薄い分野は？」）は選択ページの本文だけでは構造的に答えられない。目次は先頭固定なのでキャッシュも効く |
| 選択プロンプトの補強 | 「質問の語がそのままタイトルに含まれるページは必ず候補に入れる」（q26で「合宿」ページを選べなかった） |

### 結果

| 指標 | M2b-2（改善前） | M3（改善後） |
|---|---|---|
| ページ選択の的中 | 24/29 (82.8%) | 24/29 (82.8%) |
| 出典の明示 | 31/31 (100%) | 31/31 (100%) |
| **回答の出し方が種別に対して適切** | 21/31 (67.7%) | **23/31 (74.2%)** |
| Faithfulness | 25/31 (80.6%) | 25/31 (80.6%) |

**狙った3件がすべて直った。**

| 問い | 改善前 | 改善後 |
|---|---|---|
| q30 歴代で駆動系の課題はどう変遷したか | 「記載がありません」 | 38代のテンショナー固定法の改善から始まる変遷を記述 |
| q23 構造設計は38代から41代で何が変化したか | 「記載がありません」 | 「41代ではチームトラブルにより構造設計が不在（蒸発）」 |
| q31 最も情報が薄い分野はどこか | 「記載がありません」 | 「パイロット分野。2ページしかなくどちらも中身なし」 |

q23 はゴールデンデータの期待回答とほぼ一致した。q31 は**目次を根拠に答えており**、
回答段に目次を渡した効果が直接出ている。

**Faithfulness は 80.6% で横ばい。** 「答えられることは答える」に寄せれば
裏付けの無い記述が増えるはずだが、実測では悪化しなかった。

### 判定器の欠陥を3つ潰した

Faithfulness が一度 74.2% まで下がったが、内訳を見ると**判定器側の誤判定**だった。

| 欠陥 | 症状 | 対処 |
|---|---|---|
| 判定器が目次を見ていない | 回答段に目次を渡したのに判定器には渡しておらず、目次を根拠にした記述（q31）を「資料にない」と指摘 | 判定器にも目次を渡す |
| 出典行を主張として扱う | 「出典: 構造設計 38th（最終更新: 2022-08-21）」そのものを裏付け無しと指摘 | 出典行を判定対象から除外 |
| 判定を先に書かせていた | 判定基準の文をオウム返しする（M2bで判明） | `unsupported_claim` を先に書かせる |

この3つを潰して 80.6%。**評価器そのものを検証する工程が要る**という
docs/01 §5-3 の設計判断が、そのまま実務として必要だった。

目次はプロンプト先頭に固定してキャッシュを効かせる設計なので、サイズがそのまま費用になる。

**Bを採った。** Cは費用が3.5倍になるうえ、ローカル測定用の32kコンテキストに収まらず

### 検索精度への影響：**決着していない**

目次あり／なしで3回ずつ測るつもりだったが、**Gemini無料枠の日次上限（500リクエスト）に
当たって完走しなかった**。取れたのは各1回のみ。

| 指標 | Wikiのみ 14,741字 | 公式サイト込み 26,718字 |
|---|---|---|
| Page Recall@3 | 93.1% | 89.7% |
| 1位が正解 | 86.2% | 82.8% |

区別がつかない**。公式サイト込みが劣ると結論づけるにはデータが足りない。

→ **翌日以降に各3回ずつ測り直す。** それまで「退行なし」とは書かない。

### 評価スクリプトの欠陥をまた1つ見つけた

`toc_eval.py` が**本番と違う照合をしていた**。本番の `resolve()` は目次由来の
`（別名: X）` を剥がしてから突き合わせるのに、評価は生の文字列で比べていた。
そのため本番では引けているページを「存在しないページ名」と数え、実力を過小に報告していた。

対処として `resolve_title()` を `rag/pipeline.py` のモジュール関数に切り出し、
**評価から必ず同じ実装を使う**ようにした。結果、架空ページ名は2件 → 0件。

**測定結果が動いたら、まず測定器を疑う**という原則が、また正しかった。

### データ品質で直した2点

| 症状 | 原因 | 対処 |
|---|---|---|
| `== 2019 / Canopus ==` と見出しが2行に割れる | `<h2>2019<br>Canopus</h2>` が実在。見出しの正規表現は1行前提 | 見出しの中身を1行に畳んでから出力 |
| 記事の冒頭に記事名が3回並ぶ | テーマがパンくず・見出し・本文頭で繰り返す | 連続する同一行を1回に。**定型行の除去より後**で消す（先だと先頭行が別の行で、499/510ページで素通りしていた） |

2点目は**処理の順序だけの間違い**で、コードは正しく見えていた。実データで
「何ページ残ったか」を数えて初めて気づいた。

### 副産物：APIキーがログに漏れる経路を塞いだ

429エラーの本文を読んでいて、**例外メッセージにAPIキーがそのまま入っている**ことに気づいた。

```
RuntimeError: https://...:generateContent?key=［APIキー］ が 429: {...}
```

Gemini はキーをクエリ文字列で受け取るため、Python の `RuntimeError` にも、
Go の `*url.Error`（`log.Printf("%v", err)` でサーバーログに出る）にも鍵が載る。
**測定ログやエラーログを誰かに見せた時点で漏れる。**

両方とも `x-goog-api-key` ヘッダ渡しに変更した。Python 側には保険として
URLのキーを伏字にする `redact()` も入れてある。

## M7. 最終更新日と内容の年代の食い違い / 事実カードの追加

利用中に見つかった2つの誤答から始めた。どちらもデータの読み方の問題であって、

### きっかけになった誤答

1. 「鳥人間コンテストまでにやるべきことを教えて」に対し、

### 数字

`build_index.py` にチャンク単位の年代抽出（`extract_era`）を足して測った。
本文中の西暦（`2023年` `2023/8/25` のように区切りが続くものだけ）と代を拾い、
代は `N代 = 鳥人間コンテスト(1984+N)年大会` で西暦に直して合流させている。

| 項目 | 実測 |
|---|---|
| 全チャンク | 911 |
| 本文から年代を拾えた | 565（62%） |
| 拾えなかった | 346（38%） |
| **本文が扱う年代が最終更新より2年以上古い** | **155（17%） / 89ページ** |

食い違いの内訳（本文側の最新年）: 2022年 38件 / 2023年 25件 / 2024年 16件 ほか。

代表例が、まさに誤答1の対象だった「鳥コン」ページである。

```
（出所: Wiki / ページ: 鳥コン / 最終更新: 2026-04-12 / 本文の年代: 2024年）
```

公式サイトの「WASA60周年記念交流会のお知らせ」も同じ形で、
最終更新は2026-03だが本文の日付は**2025年11月**である。

### 読み取れたこと

- **`last_edited` を情報の鮮度として使うのは誤り。** 6件に1件で2年以上ずれる。
  誤字直しやリンク追加でも更新日は今日になるので、原理的にずれる指標だった
- **代（世代）は西暦に決定的に変換できる。** `N代 = (1984+N)年大会` は、
  公式サイトの歴史ページの全代（1985年=初代 / 2005年=21代 / 2015年=31代）と、
  Wiki側の「2024年度執行代（40代）」「2026年TF(42nd)」のすべてに例外なく一致する。
  LLMに推測させる必要はない
- **既存の `GEN_BODY` は日本語で最も普通の書き方に当たらない。**
  `\b(3[0-9]|4[0-9])\s*(?:st|nd|rd|th|代)\b` は、Pythonの `\b` が日本語の文字も
  語構成文字とみなすため「42代の引き継ぎ」「第42代」のどちらにもマッチしない。
  ページ単位の `gen` はこの挙動のまま M2a の数字を出しているので触っていないが、
  **`gen` の抽出率（不明484件）はこれが理由で低く出ている可能性が高い**。要再測定
- **60周年の誤りは検索でもプロンプトでも直らない。** 資料には
  「WASAは1965年設立」も「WASA60周年」も「鳥人間は1985年」も正しく書いてあり、
  どれを引いても矛盾しない。**足りないのは2つが別の単位だという知識**である

### 判断を変えた点

- **今日の日付をプロンプトに渡す。** 日本時間で `answerPrompt` の先頭に入れる。
  Cloud RunのコンテナはUTCなので、JSTへの変換を明示する
- **チャンクに「本文の年代」を持たせ、資料ブロックに添える。**
  回答プロンプト側では「古さの判断は最終更新日ではなく本文の年代を根拠にする」
  「本文の年代が無いときは古さを断定しない」と指示する。空欄を出すと
  「不明」が「古い」に読み替えられるため、拾えなかったときは項目ごと省く
- **人が保守する事実カード `facts.md` を新設する。** `build_toc.py` が
  `data/toc.md` の先頭に埋め込む。目次は「先頭に固定するとキャッシュが効く」
  条件で設計されているため、目次の先頭に入れればキャッシュの条件も配置も変わらない。
  現在975字（目次全体の3.7%）。**「実際に誤答した」根拠のある事柄だけを書く**
- **資料ブロックにページURLを添え、出典をMarkdownリンクで出させる。**

### 読み取れたこと

- **「資料にあるのに記載なし」は回答プロンプトでは直らない。** TR797は目次の
  ページ名・リード文・上位見出しに現れず、ページを開く前の段階で落ちていた
- **BM25を入れるだけでも型番が必ず上位になるとは限らない。** 今回は完全一致語を
  含む正解チャンクが22位で、上位5件の回答文脈には入らなかった
- `TR797` / `TR-797` のような記号差は意味推論ではなく、決定的な正規化で扱える

### 判断を変えた点

- 目次方式だけで進める方針は維持するが、**英字で始まり数字を含む4文字以上の型番**が
  質問にある場合だけ、全チャンクを正規化完全一致で総当たりする軽量経路を追加した
- ハイフンとアンダースコアを除いて小文字化し、一致ページ上位2件をLLMの選択結果へ
  合流する。4枠すべてを完全一致で埋めず、質問全体を見たLLM候補を2枠以上残す。
  長いページから節を8件へ絞る段でも、型番一致チャンクを先に残す
- TR797を `facts.md` へは追加しない。資料本文に説明があるため、事実カードで
  検索漏れを隠さず、検索経路とゴールデンデータで再発を防ぐ
