# WASA Chat 引き継ぎガイド

この文書は、WASA Chatの引き継ぎをする人が初めに見るべき文書です。

色々な文書につながっていますが、もちろん最初から全部を理解する必要はありません。

まずこのページを読み、作業に関係する文書だけを開いてください。

## 最初に知っておく言葉

まず初めに、知っておくべき専門用語をここに載せておきます。

この先の文書では説明なしにこれらの言葉が出てきます。ここで一度目を通しておくと、
あとの文書がぐっと読みやすくなるはずです。

- **フロントエンド**: 利用者がブラウザで見る画面です。`web/`にあります。
- **バックエンド**: ログイン、資料検索、AIへの質問、保存を行うサーバーです。`backend/`にあります。
- **索引（インデックス）**: Wikiや公式サイトを、質問から探しやすい形へ整理したファイルです。
- **チャンク**: 長い資料を見出しごとに分けた、検索の単位です。
- **Firestore**: Google Cloud上の保存場所です。履歴、利用回数、フィードバックを保存します。
- **SMTP**: WASA Chatからメール送信サービスへ、通知メールを渡す方法です。
- **デプロイ**: 手元で直したものを、本番で使える状態にする作業です。

## 普段の運用

WASA Chatは、Wikiと公式サイトの内容をあらかじめ取り込んで索引にしています。

つまり、**Wikiが更新されても、WASA Chatが自動で新しくなるわけではありません。**
誰かが取り込み直す作業をして、初めて新しい内容に答えられるようになります。
その作業が、ここで説明する2つのコマンドです。

まず、Wikiや公式サイトに変更があったかどうかを確認します。

```bash
python check_updates.py
```

変更が見つかったら、取得・索引作成・検索検査をまとめて行います。

```bash
python rebuild.py
```

ここで大事なのは、**`rebuild.py`は自動で本番公開しない**ということです。

これはわざとそうしています。非公開Wikiの内容が正しく取得できたかどうかを、
公開する前に人の目で確かめてほしいからです。誰かがWikiを間違えて編集していた場合、
自動で公開する仕組みだと、その間違いがそのまま利用者への回答になってしまいます。

確認が済んだあとの公開手順は[04-デプロイ手順.md](04-デプロイ手順.md)にあります。

利用者から届いたフィードバックは、次の2か所で確認できます。

- 管理者でログインした画面の「改善を送る」
- `FEEDBACK_EMAIL_TO`に設定したメールアドレス

なお、メール送信に失敗しても内容はFirestoreに残ります。メールが届かなかったからといって、
報告が消えてしまうわけではないので安心してください。

## どの文書を直すか

文書が複数あると、「これはどこに書けばいいんだろう」と迷うことがあると思います。

同じことが2つの文書に書いてあると、片方だけ直したときに食い違いが生まれます。
実際に過去そうなったことがあるので、**どの話題はどの文書が正本（オリジナル）なのか**を
ここではっきり決めておきます。

| 直したい内容 | 正本 | 具体例 |
|---|---|---|
| 設計判断の理由 | `docs/01-設計方針.md` | RAG方式、認証方式、デプロイ構成、段階的導入 |
| 数字と誤答の記録 | `docs/02-測定結果.md` | Recall、チャンク数、誤答分類、モデル比較、再現コマンド |
| 現在の画面挙動 | `docs/03-画面仕様.md` | 履歴、アシスタント切り替え、通知 |
| 本番作業 | `docs/04-デプロイ手順.md` | デプロイ、更新、ロールバック |
| モデルへ渡す文章と入力順 | `docs/05-システムプロンプト.md` | 役割、タスク、規則、組み立て順 |
| モデルに頼らずコードで決める規則 | `docs/06-決定的ルール.md` | 入力上限、参照範囲、型番一致 |
| 認証・保存・データ保護 | `docs/07-認証・データ保護.md` | ログイン、Cookie、Firestore |

ただし、プロンプトと決定的ルールについては注意点があります。

**実際に動いているものの最終的な正本はコードです。** 文書はあくまで「何のためにその規則があるか」を
説明するものなので、文書とコードが食い違っていたらコードが正しいと考えてください。
該当するコードは次の場所にあります。

- プロンプト: `backend/internal/assistant/assistant.go` と `backend/internal/pipeline/pipeline.go`
- 決定的ルール: 対応するGo / Pythonコード

## 機能を変えるときの確認先

機能を変えるときは、先に該当する文書を読んでおくと事故が減ります。

ここでは変更の種類ごとに、読むべき文書と、実際にやってほしい確認をまとめています。
特に「してはいけないこと」を書いてあるものは、過去に実際に問題が起きた箇所です。

**プロンプトを変えるとき**

- `docs/05-システムプロンプト.md`の責務と入力順を確認します
- 本番Goと測定用Pythonの共通部分を、両方とも更新します
- ただし、アシスタント固有のsystem規則・範囲制限は本番Goだけにあります。
  片方だけ直して「差を消した」と思い込まないでください
- ゴールデンデータ全体で推論し、ミス・指摘漏れ・過剰検知を分類します

**検索やマスキングを変えるとき**

- `docs/06-決定的ルール.md`と`build_index.py`を確認します
- 数字を測り、`docs/02-測定結果.md`へ再現コマンドと結果を残します

**ログイン・Cookie・Firestoreを変えるとき**

- `docs/07-認証・データ保護.md`を確認します
- 認証方式や個人情報の扱いは、技術的に正しいというだけで変えないでください。
  サークルのデータに関わる判断なので、必ず人間に確認します

**画面を変えるとき**

- `docs/03-画面仕様.md`を確認します
- `npm run build`が通ることと、狭い画面で要素が重ならないことを確認します

**本番設定を変えるとき**

- `docs/04-デプロイ手順.md`を確認します
- `min-instances=0`と、初期運用の`max-instances=1`は維持します（費用と送信制限に直結します）

## 最低限の検証

何かを直したら、最低限これだけは実行してください。

3つとも数秒〜十数秒で終わりますし、ここで落ちるものを本番へ持っていくと、
原因を探すのに何倍も時間がかかります。

```bash
cd backend
GOCACHE=/private/tmp/wasa-go-cache go test ./...

cd ../web
npm run build

cd ..
python -m py_compile rag/pipeline.py eval/response_mode_eval.py
```

テストを動かすうえで知っておいてほしいことが3つあります。

- 実Wikiの認証は、通常の単体テストでは外部通信しません。テストのたびにWikiへ
  アクセスしにいくことはないので、気軽に実行して大丈夫です
- 実Wikiで確かめたいときだけ、秘密値を`.env`へ置いて`LIVE_WIKI_TEST=1`を付けます
- 非公開の`dump/`、`data/`、`.env`、`eval/golden.json`はコミットしないでください。
  これらには非公開Wikiの中身が入っています
